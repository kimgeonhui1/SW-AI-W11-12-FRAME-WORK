### README 맨 위 · 0:00 \~ 0:15

안녕하세요, Mini Redis 발표를 맡은 김건희입니다.  
Redis 같은 저장소를 직접 만들어서, 느린 API 앞에 캐시로 붙여 봤습니다.  


### 1. 구현 방식 그림 · \~0:40

먼저 전체 흐름입니다.  
사용자가 데이터를 요청하면, 바로 원본에 가지 않고 Mini Redis부터 확인합니다.  
여기에 값이 있으면 그대로 돌려주고,  
없을 때만 0.2초 걸리는 원본에 가서 가져오고, 다음번을 위해 저장해 둡니다.  


### 2. 해시 테이블 그림 → 구현 표 → 무효화 그림 · \~1:40

다음은 저장소 안쪽입니다.  
값을 빠르게 찾으려면 키만 보고 몇 번 버킷에 있는지 바로 알아야 해서, 문자열인 키를 먼저 숫자로 바꿉니다.  
이때 쓰는 게 FNV-1a라는 해시 함수입니다. 1991년에 공개된 알고리즘입니다.  
글자를 하나씩 읽으면서 숫자를 섞어 나가는 방식이라, 같은 키면 언제나 같은 숫자가 나옵니다.  
파이썬 hash()는 켤 때마다 값이 바뀌어서, 충돌 테스트를 재현하려고 FNV-1a를 골랐습니다.  
이 숫자를 버킷 개수로 나눈 나머지가 곧 버킷 번호가 됩니다.  
서로 다른 키가 같은 버킷에 들어가는 충돌은 체이닝 방식으로 해결했습니다.  
버킷마다 목록을 두고, 충돌한 키를 그 목록 뒤에 이어 붙이는 방식입니다.  
버킷이 75% 정도 차면 버킷 수를 두 배로 늘려서, 찾는 속도가 느려지지 않게 했습니다.  

*(표를 가리키며)*
요청이 동시에 들어오니까, 명령은 락으로 감싸 한 번에 하나씩 실행되게 했습니다.  
시간이 지나면 사라지는 값은, 읽을 때 확인해서 지우고 1초마다 한 번씩 정리도 합니다.  

*(무효화 그림을 가리키며)*
제일 오래 고민했던 건 캐시를 언제 지우느냐였습니다.  
누가 가격을 조회하는 사이에 다른 사람이 가격을 바꾸면,  
조회가 바뀌기 전 가격을 캐시에 넣어 버려서, 원본은 5원인데 캐시는 100원이 됩니다.  
그래서 캐시 키에 버전 번호를 붙였습니다.  
그러면 옛 가격은 옛 버전에만 들어가고, 새 조회는 새 버전만 봅니다.  


### 3. Pintos와 비교 표 · \~2:30

만들면서 재밌었던 점은, 지난주에 했던 Pintos 개념이 계속 다시 나왔다는 것입니다.  

첫 번째는 락입니다.  
Pintos에서는 락 푸는 코드를 한 군데만 빠뜨려도 멈춰 버렸습니다.  
파이썬은 with 문을 쓰면 에러가 나도 자동으로 풀어 줍니다.  

두 번째는 lazy loading입니다.  
Pintos는 페이지를 실제로 쓸 때 불러오고, Mini Redis는 값을 실제로 읽을 때 만료를 확인해 지웁니다.  
불러오느냐 지우느냐만 다르고, 필요한 순간까지 미룬다는 생각은 같습니다.  

세 번째는 fork할 때의 copy-on-write입니다.  
실제 Redis는 저장할 때 fork로 그 순간의 모습을 떠서 파일로 남기는데,  
저도 락 안에서 데이터만 빠르게 복사하고 파일 쓰기는 밖에서 했습니다.  


### 4. 성능 측정 그래프 → 결과 표 · \~3:05

결과를 보면, 캐시가 있을 때 응답이 205ms에서 3ms 정도로 줄었습니다.  
50명이 동시에 요청하면 원본은 1초에 25건에서 막히는데, 캐시를 쓰면 327건까지 처리했습니다.  


### 5. 회고 표 · \~3:20

이번에 가장 크게 배운 건 측정하는 도구부터 의심해야 한다는 점이었습니다.  
결과가 매번 크게 달라서 찾아보니, 캐시가 아니라 Windows에서 연결을 맺는 방식 때문이었습니다.  
AI 리뷰도 그대로 믿지 않고, 직접 재현해 보고 맞는 것만 고쳤습니다.  
이상으로 발표 마치겠습니다. 감사합니다.

## 예상 질문
**Q. FNV-1a는 안전한가요?**
A. 암호용 해시가 아니라서, 일부러 같은 버킷에 몰리는 키만 골라 보내면 느려질 수 있습니다. 파이썬 hash()가 실행마다 값을 바꾸는 이유가 바로 이 공격(hash flooding)을 막기 위해서입니다. 이번 과제에서는 테스트 재현성을 우선했습니다.


**Q. 체이닝은 보통 연결 리스트로 하지 않나요?**
A. 교과서에서는 보통 연결 리스트로 구현합니다. 저는 버킷이 75% 차면 두 배로 늘려서 버킷마다 키가 몇 개뿐이라, 파이썬 리스트로 충분했습니다.


**Q. 락이 하나면 느리지 않나요?**
A. 명령 하나가 메모리만 잠깐 건드리고 끝나서, 지금 규모에서는 문제가 없었습니다. 대신 CPU 코어 여러 개를 동시에 쓰지는 못합니다.


**Q. 서버가 갑자기 꺼지면 데이터는요?**
A. 60초마다 파일로 저장하기 때문에, 마지막 저장 이후에 바뀐 건 잃습니다. 캐시는 원본에서 다시 채우면 되니까 이 방식을 골랐습니다.


**Q. 정확히 몇 배 빨라졌나요?**
A. 원본이 0.2초 걸릴 때, 실행할 때마다 45배에서 72배 사이였습니다.


**Q. 실제 Redis와 가장 큰 차이는요?**
A. 실제 Redis는 스레드 하나로 수천 개 연결을 처리하고, 저는 연결마다 스레드를 하나씩 씁니다. 통신도 Redis 전용 방식 대신 HTTP와 JSON을 썼습니다.
