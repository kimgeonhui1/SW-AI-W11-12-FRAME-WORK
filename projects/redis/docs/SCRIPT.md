# Mini Redis 발표 대본 (약 3분 30초)

README를 화면에 띄우고 위에서부터 내려가며 읽습니다. 괄호 안은 화면 위치와 누적 시간입니다.

---

### 0. 인사 (README 맨 위 · ~0:15)

안녕하세요, Mini Redis를 발표할 김건희입니다.
해시 테이블부터 직접 만든 저장소를 느린 API 앞에 캐시로 붙여 봤습니다.
외부 라이브러리 없이 만들었고, 테스트 174개가 모두 통과합니다.

### 1. 무엇을 만들었나 (구조 그림 · ~0:40)

구조는 이 그림과 같습니다.
사용자가 데모 API에 요청하면, 먼저 Mini Redis를 봅니다.
있으면 바로 응답하고, 없으면 0.2초 걸리는 원본을 조회한 뒤 Mini Redis에 저장합니다.
Mini Redis가 꺼져도 원본으로 우회해서 API는 계속 동작합니다.

### 2. 핵심 설계 (해시 테이블 그림 → 표 → 경쟁 상태 그림 · ~1:40)

저장소는 파이썬 dict 대신 해시 테이블을 직접 만들었습니다.
키를 FNV-1a로 숫자로 바꾸고, 칸 수로 나눈 나머지 칸에 넣습니다.
같은 칸에 오면 목록에 이어 붙이고, 75%가 차면 칸을 두 배로 늘립니다.

여러 요청이 동시에 들어오기 때문에 모든 명령을 락 하나로 감쌌습니다.
만료는 실제 Redis처럼 두 가지를 같이 씁니다.
읽을 때 지우는 건 정확성, 1초마다 지우는 건 메모리를 위해서입니다.

가장 고민한 건 캐시 무효화입니다.
조회가 원본을 읽는 사이에 가격이 바뀌면, 조회가 옛 가격을 캐시에 다시 넣어 버립니다.
그래서 캐시 키에 버전을 넣어, 옛 값은 옛 키에만 들어가게 했습니다.

### 3. 지난주 Pintos와 같은 발상 (Pintos 표 · ~2:30)

만들면서 지난주 Pintos에서 본 개념이 그대로 다시 나왔습니다.

첫째, 락입니다. Pintos에서는 release를 하나만 빠뜨려도 데드락이었죠.
파이썬의 with는 어떤 경로로 나가도 자동으로 풀어 줍니다.

둘째, 지연 로딩과 지연 삭제입니다.
Pintos는 페이지를 실제로 접근할 때 읽어 오고, Mini Redis는 키를 실제로 읽을 때 만료를 확인합니다.
하나는 만드는 일을, 하나는 지우는 일을 필요한 순간까지 미루는 겁니다.

셋째, fork의 copy-on-write입니다.
실제 Redis는 fork한 자식이 그 순간의 사진을 디스크에 씁니다.
저는 락 안에서 사진만 찍고, 느린 파일 쓰기는 락 밖에서 했습니다.

### 4. 성능 (그래프 두 개 → 표 · ~3:05)

같은 요청을 캐시로 받으면 205ms가 3ms로, 약 70배 빨라졌습니다.
다만 원본이 이미 빠르면 캐시가 오히려 느렸습니다.
동시 50명에서는 원본이 초당 25건에서 막히는데, 캐시는 327건을 처리했습니다.

### 5. 회고 (회고 표 · ~3:30)

가장 크게 배운 건 측정 도구부터 의심하는 것입니다.
결과가 크게 흔들렸는데, 원인은 캐시가 아니라 Windows의 연결 지연이었습니다.
그리고 AI 리뷰는 직접 재현되는 것만 고쳤습니다.
감사합니다.

## 예상 질문

| 질문 | 답 |
|---|---|
| 왜 파이썬 `hash()`를 안 썼나요? | 실행할 때마다 값이 바뀌어서, "이 두 키는 충돌한다" 같은 테스트를 재현할 수 없기 때문입니다. FNV-1a는 항상 같은 값입니다. |
| 락 하나면 느리지 않나요? | 명령 하나가 메모리 작업이라 아주 짧아서 지금 규모에선 문제없습니다. 대신 코어를 여러 개 쓰지는 못합니다. |
| 서버가 갑자기 꺼지면요? | 마지막 스냅샷 이후 변경은 잃습니다. 캐시라서 원본에서 다시 채우면 되므로 스냅샷 방식을 골랐습니다. |
| 실제 Redis와 가장 큰 차이는? | 실제 Redis는 스레드 하나가 이벤트 루프로 수천 연결을 처리하고, 저는 연결마다 스레드를 씁니다. 통신도 RESP 대신 HTTP JSON입니다. |
