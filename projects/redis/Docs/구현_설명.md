## 0. 한눈에 보기

**Redis** 는 데이터를 메모리에 "키 → 값" 으로 저장하는 아주 빠른 저장소입니다. 주로 **캐시**(느린 DB 결과를 잠깐 저장해 두고 다시 쓰기)로 씁니다.
Mini Redis 는 그 핵심만 파이썬으로 직접 만든 것입니다.

| 만든 것 | 파일 | 한 줄 설명 |
|---|---|---|
| 해시 테이블 | `mini_redis/hashtable.py` | 파이썬 `dict` 없이 "키 → 값" 을 평균 O(1) 로 찾는 자료구조 |
| 저장소 | `mini_redis/store.py` | 해시 테이블 위에 **만료(TTL)** 와 **여러 스레드 동시 접근 제어(락)** 를 얹은 Mini Redis 본체 |
| HTTP 서버 | `mini_redis/server.py` | 다른 프로그램이 HTTP + JSON 으로 저장소를 쓰게 해 주는 서버 |
| 캐시 데모 | `demo/api_server.py` | 0.2초 걸리는 "느린 DB" 앞에 Mini Redis 를 캐시로 붙인 예제 API |
| 벤치마크 | `demo/benchmark.py` | 캐시를 쓸 때 / 안 쓸 때 응답 시간 비교 |

```
 Client          demo/api_server.py · demo/benchmark.py · curl
   │ HTTP JSON
 API Server      mini_redis/server.py      요청 읽기 · 입력 검사 · JSON 응답 · 1초마다 만료 키 정리
   │ 메서드 호출 (set / get / delete / expire / ttl ...)
 Command Layer   mini_redis/store.py       MiniRedis: 만료(TTL) · 락 · Redis 규칙(-1 / -2)
   │ get / set / delete / keys
 Storage Engine  mini_redis/hashtable.py   HashTable: FNV-1a 해시 · 체이닝 · 리사이즈
```

**계층 규칙: 아래는 위를 모른다.**
- 해시 테이블은 "만료" 라는 개념이 없습니다. 그냥 키와 값을 저장합니다.
- 저장소는 HTTP 를 모릅니다. 파이썬 메서드로만 불립니다.
- 그래서 각 층을 따로 테스트할 수 있고, 한 층을 바꿔도 다른 층은 그대로입니다.

## 1. 요청 하나의 여행 — 처음부터 끝까지

아래 두 요청이 서버 안에서 어떤 길을 지나가는지 따라가 봅니다.

```bash
curl -X PUT localhost:6380/keys/user:1 -d '{"value": "Nameisme", "ttl": 60}'
curl localhost:6380/keys/user:1
```

### 1-1. 저장 `PUT /keys/user:1`

| 단계 | 어디서 | 무슨 일 |
|---|---|---|
| ① | 운영체제 | 연결이 들어오면 **연결 대기열**(최대 128개)에 줄을 선다 |
| ② | `ThreadingHTTPServer` | 연결 하나마다 **새 스레드**를 만들고 `Handler` 객체를 하나 만든다 |
| ③ | `Handler.setup` (`server.py:55`) | 이 연결의 읽기 제한 시간을 10초로 정한다 |
| ④ | `do_PUT` → `_handle("PUT")` (`server.py:62`, `:79`) | 모든 메서드가 `_handle` 한 곳으로 모인다 |
| ⑤ | `_route` (`server.py:89`) | 경로 `/keys/user:1` 을 `/` 로 나눔 → `["keys", "user:1"]` → "키 하나짜리 경로 + PUT" 으로 판단 |
| ⑥ | `_read_json` (`server.py:142`) | Content-Length 확인 → 본문 읽기 → JSON 해석 → 객체인지 · 다시 쓸 수 있는 값인지 검사 → `{"value": "Nameisme", "ttl": 60}` |
| ⑦ | `_route` | `value` 가 있고 `null` 이 아님을 확인 |
| ⑧ | `_call(store.set, ...)` (`server.py:135`) | 저장소 호출. ttl 이 잘못이면 저장소가 `ValueError` → 서버가 400 으로 바꾼다 |
| ⑨ | `MiniRedis.set` (`store.py:52`) | ttl 검사(락 밖) → **락 잡기** → `_data` 에 값 저장 → `_expires` 에 "지금 + 60초" 저장 → 락 놓기 |
| ⑩ | `HashTable.set` (`hashtable.py:78`) | `fnv1a("user:1")` = `0xf7fd9aaa75081ceb` → `% 8` = **3번 칸** → 칸에 같은 키가 없으니 `["user:1", "Nameisme"]` 를 붙임 |
| ⑪ | `_send` (`server.py:188`) | `{"ok": true}` 를 JSON 으로 바꿔 `200` 과 함께 보낸다 |

### 1-2. 조회 `GET /keys/user:1`

| 단계 | 어디서 | 무슨 일 |
|---|---|---|
| ① ~ ⑤ | 위와 같음 | `_route` 가 "키 하나짜리 경로 + GET" 으로 판단 |
| ⑥ | `store.get_with_ttl` (`store.py:71`) | **락 하나 안에서** 값과 남은 시간을 함께 읽는다 |
| ⑦ | `_alive` (`store.py:125`) | 키가 있나? 만료 시각이 지났나? → 살아 있음 |
| ⑧ | `_ttl_left` (`store.py:136`) | 만료 시각 − 지금 = 59.97… → **올림** → `60` |
| ⑨ | `_send` | `200 {"key": "user:1", "value": "Nameisme", "ttl": 60}` |

60초가 지난 뒤 같은 요청을 보내면 ⑦ 에서 "만료됨" 으로 판단해 **그 자리에서 지우고**(지연 삭제) `404 {"error": "키가 없습니다"}` 를 보냅니다.
아무도 다시 읽지 않아도, 서버의 정리 스레드가 1초마다 `sweep()` 을 불러 메모리에서 지웁니다(주기 삭제).

## 2. 해시 테이블 — `hashtable.py`

### 2-1. 왜 해시 테이블인가

키로 값을 찾을 때 리스트를 처음부터 훑으면 키가 n 개일 때 최악 n 번 비교합니다(O(n)).
해시 테이블은 **키를 숫자로 바꿔 그 숫자 번째 칸으로 바로 갑니다.** 칸 안에 항목이 한두 개뿐이면 비교도 한두 번이라 평균 O(1) 입니다.
과제 규칙상 파이썬 `dict`(그 자체가 해시 테이블)는 쓸 수 없어서 직접 만들었습니다.

### 2-2. 생김새 — 칸(bucket)마다 리스트 (Separate Chaining)

```python
self._buckets = [[] for _ in range(capacity)]   # hashtable.py:56  처음 8칸
self._size = 0                                  # hashtable.py:57  저장된 항목 수
```

`k0` ~ `k5` 6개를 넣은 뒤 실제 모습 (8칸):

```
_buckets
├── [0] [ ["k2", 2] ]
├── [1] [ ["k1", 1] ]
├── [2] [ ["k4", 4] ]
├── [3] [ ["k3", 3] ]
├── [4] [ ]
├── [5] [ ["k5", 5] ]
├── [6] [ ["k0", 0] ]
└── [7] [ ]
```

- 칸 하나 = 파이썬 리스트. 그 안의 항목 하나 = `[key, value]` **리스트**.
  튜플이 아니라 리스트인 이유: 같은 키에 다시 저장할 때 `entry[1] = value` 로 값만 바꾸면 되기 때문입니다.
- `[[]] * n` 이 아니라 `[[] for _ in range(n)]` 으로 만드는 이유: `[[]] * n` 은 **같은 리스트 하나를 n 번 가리킵니다.** 한 칸에 넣으면 모든 칸에 들어간 것처럼 보입니다.
- `_size` 를 따로 세는 이유: `len(table)` 을 부를 때마다 모든 칸을 세면 O(n) 입니다. 넣고 뺄 때 1씩 바꿔 두면 O(1) 입니다.

### 2-3. 키 → 숫자: FNV-1a 해시 (`hashtable.py:38`)

```python
FNV_OFFSET = 0xCBF29CE484222325   # 시작 값 (표준)
FNV_PRIME  = 0x100000001B3        # 곱하는 소수 (표준)
MASK_64    = (1 << 64) - 1        # 64비트로 자르기

def fnv1a(key):
    if not isinstance(key, str):
        raise TypeError(...)
    h = FNV_OFFSET
    for byte in key.encode("utf-8", "surrogatepass"):
        h ^= byte                         # 1) 바이트를 섞고 (XOR)
        h = (h * FNV_PRIME) & MASK_64     # 2) 소수를 곱해 퍼뜨린 뒤 64비트로 자른다
    return h
```

**실제 계산 — `fnv1a("ab")`**

| 단계 | 바이트 | XOR 결과 | × 소수 후 64비트로 자름 |
|---|---|---|---|
| 시작 | — | — | `0xcbf29ce484222325` |
| 1 | `0x61` (`a`) | `0xcbf29ce484222344` | `0xaf63dc4c8601ec8c` |
| 2 | `0x62` (`b`) | `0xaf63dc4c8601ecee` | `0x089c4407b545986a` |

→ `fnv1a("ab") = 0x089c4407b545986a`, 8칸이면 `% 8` = **2번 칸**.

**왜 이렇게 하나**
- **XOR 다음 곱하기**: 글자 하나만 달라도 결과 전체가 크게 달라집니다. 그래야 키들이 칸에 고르게 퍼집니다. (XOR 을 먼저 하는 게 FNV-1a, 곱하기를 먼저 하는 게 FNV-1)
- **`& MASK_64`**: 파이썬 정수는 한없이 커지므로, C 언어의 64비트 정수처럼 넘친 부분을 잘라 냅니다.
- **파이썬 내장 `hash()` 를 안 쓰는 이유**: 문자열의 `hash()` 는 프로그램을 켤 때마다 값이 바뀝니다(`PYTHONHASHSEED`, 해시 공격 방지용). 그러면 "이 키가 몇 번 칸에 들어가는지" 를 테스트에서 재현할 수 없습니다. FNV-1a 는 언제나 같은 값입니다.
- **UTF-8 바이트로 계산**: 한글 `메이플` 도 바이트 9개로 바뀌어 똑같이 계산됩니다 (`0xfcd5f29a0311e98f`, 8칸이면 7번).
- **`surrogatepass`**: 파이썬 문자열에는 짝 없는 반쪽 문자(`"\ud800"`)가 들어갈 수 있는데, 그냥 UTF-8 로 바꾸면 `UnicodeEncodeError` 가 납니다. 이 옵션을 주면 오류 없이 바이트로 바뀝니다.
- **문자열이 아니면 `TypeError`**: 숫자 `123` 을 키로 넣으면 `.encode` 에서 이상한 오류가 나기 전에, "키는 문자열이어야 합니다 (받은 타입: int)" 로 원인을 바로 알려 줍니다.

### 2-4. 숫자 → 칸 번호 (`hashtable.py:107`)

```python
def _index(self, key):
    return fnv1a(key) % len(self._buckets)
```

| 키 | `fnv1a(key)` | 8칸일 때 | 16칸일 때 |
|---|---|---|---|
| `user:1` | `0xf7fd9aaa75081ceb` | 3 | 11 |
| `name` | `0xc4bcadba8e631b86` | 6 | 6 |
| `메이플` | `0xfcd5f29a0311e98f` | 7 | 15 |
| `hi` | `0x08ba5f07b55ec3da` | **2** | **10** |
| `post:9` | `0x004585d7b76370ba` | **2** | **10** |

같은 키라도 **칸 수가 바뀌면 칸 번호가 바뀝니다** (`user:1` 은 3 → 11). 그래서 리사이즈 때 모든 항목을 다시 넣어야 합니다 (2-7).

### 2-5. 충돌 — 다른 키가 같은 칸에 올 때

위 표에서 `hi` 와 `post:9` 는 서로 다른 키인데 같은 2번 칸입니다. 이것이 **충돌**입니다. 칸 수는 유한하고 키는 무한하니 충돌은 반드시 생깁니다.

체이닝은 충돌을 이렇게 처리합니다: **같은 칸의 리스트에 그냥 하나 더 붙입니다.**

```
[2] [ ["hi", ...], ["post:9", ...] ]
```

찾을 때는 2번 칸 리스트를 앞에서부터 보며 키가 **정확히 같은** 항목을 찾습니다 (`entry[0] == key`). 해시가 같아도 키 문자열을 직접 비교하므로 섞이지 않습니다.

**왜 체이닝인가 (다른 방법: 개방 주소법)**
개방 주소법은 칸이 차 있으면 옆 칸으로 가서 빈 곳을 찾습니다. 문제는 **삭제**입니다. 중간 항목을 그냥 비우면, 그 뒤로 밀려나 있던 항목을 찾다가 빈 칸에서 "없다" 고 멈춰 버립니다. 그래서 "삭제됨" 표시(tombstone)를 따로 관리해야 합니다.
체이닝은 리스트에서 빼면 끝이라 코드가 짧고 실수할 곳이 적습니다.

### 2-6. 저장 · 조회 · 삭제

```python
def set(self, key, value):                                   # hashtable.py:78
    bucket = self._buckets[self._index(key)]
    for entry in bucket:
        if entry[0] == key:
            entry[1] = value          # 같은 키 → 값만 바꿈. 항목 수 그대로
            return
    bucket.append([key, value])       # 새 키 → 칸 리스트 끝에 붙임
    self._size += 1
    if self._size / len(self._buckets) > MAX_LOAD_FACTOR:
        self._resize(len(self._buckets) * 2)
```

- 덮어쓰기는 `_size` 가 그대로라 리사이즈 검사도 하지 않습니다.
- `get(key, default=None)` (`:73`) 은 `_find` 로 항목을 찾아 `entry[1]` 을, 없으면 `default` 를 돌려줍니다.
- `delete(key)` (`:90`) 는 칸 리스트에서 `del bucket[i]` 로 빼고 `_size` 를 1 줄입니다. 지웠으면 `True`, 없던 키면 `False`.
- `key in table` (`__contains__`, `:69`) 은 **값이 `None` 인 키도 "있음"** 으로 답합니다. `get` 은 "값이 None" 과 "키가 없음" 을 구별할 수 없기 때문에 따로 둡니다. 저장소가 이걸 씁니다.
- `keys()` (`:101`) 는 **새 리스트**를 만들어 돌려줍니다. 그래서 "키 목록을 돌면서 지우기"(저장소의 `sweep`)를 해도 반복 도중 리스트가 바뀌어 키를 빠뜨리는 일이 없습니다.

### 2-7. 리사이즈 — 부하율 0.75 를 넘으면 칸 2배

**부하율** = 항목 수 ÷ 칸 수. 부하율이 높으면 한 칸에 항목이 여러 개 줄 서서 찾기가 느려집니다.

실제로 `k0` ~ `k6` 을 차례로 넣어 보면:

| 넣은 키 | 항목 수 | 칸 수 | 부하율 | |
|---|---|---|---|---|
| `k0` ~ `k5` | 1 → 6 | 8 | 0.125 → **0.750** | 0.75 는 "넘지" 않았으므로 그대로 |
| `k6` | 7 | 8 → **16** | 0.875 → 0.438 | 넘는 순간 2배 |

리사이즈 뒤 16칸의 모습 — 칸 번호가 새로 계산되어 흩어졌습니다:

```
[1] k1   [4] k6   [8] k2   [10] k4   [11] k3   [13] k5   [14] k0   (나머지는 빈 칸)
```

```python
def _resize(self, new_capacity):                             # hashtable.py:119
    new_buckets = [[] for _ in range(new_capacity)]
    for bucket in self._buckets:
        for entry in bucket:
            new_buckets[fnv1a(entry[0]) % new_capacity].append(entry)
    self._buckets = new_buckets
```

- 항목 리스트 `[key, value]` 는 새로 만들지 않고 **그대로 옮깁니다.**
- 키들이 서로 다르다는 것이 이미 보장되므로 "같은 키 있나?" 검사도 하지 않습니다.
- 리사이즈 한 번은 O(n) 이지만, 칸이 2배씩 늘어서 아주 가끔만 일어납니다. 평균 내면 저장 한 번당 O(1) 입니다 (분할 상환).
- **줄이지는 않습니다.** 지운 뒤 다시 채우는 경우가 많고, 줄이는 코드는 경계 실수가 생기기 쉽습니다.
- `capacity()` (`:64`) 로 지금 칸 수를 볼 수 있습니다 (테스트가 리사이즈를 확인할 때 씀).

### 2-8. 입력 검사

| 입력 | 결과 | 이유 |
|---|---|---|
| `HashTable(capacity=0)` | `ValueError` | `% 0` 은 0 으로 나누기 |
| `HashTable(capacity=1.5)` · `"8"` | `ValueError` | `range()` 에서 알 수 없는 오류가 나기 전에 분명하게 |
| `HashTable(capacity=True)` | `ValueError` | 파이썬에서 `True` 는 `int` 의 한 종류(=1)라 `type(x) is int` 로 따로 막음 |
| 키가 `123` · `None` · `b"bytes"` | `TypeError` | `fnv1a` 에서 바로 |

### 2-9. 시간 복잡도

| 동작 | 평균 | 최악 (모든 키가 한 칸) |
|---|---|---|
| `get` · `set` · `delete` · `in` | O(1) | O(n) |
| `len` · `capacity` | O(1) | O(1) |
| `keys` · `_resize` | O(n) | O(n) |

## 3. 저장소 — `store.py`

해시 테이블은 "키 → 값" 만 압니다. 저장소 `MiniRedis` 는 그 위에 Redis 다운 기능을 얹습니다.

### 3-1. 해시 테이블 두 개 (`store.py:44`)

```python
def __init__(self, clock=time.monotonic):
    self._clock = clock
    self._data = HashTable()       # 키 → 값
    self._expires = HashTable()    # 키 → 만료 시각 (ttl 을 준 키만)
    self._lock = threading.Lock()
```

```
_data                          _expires
"user:1" → "Nameisme"          "user:1" → 12345.67   (이 시각이 되면 만료)
"config" → {"dark": true}      (없음 = 만료 없음)
```

- 실제 Redis 도 값과 만료 시각을 따로 저장합니다.
- **만료가 있는 키만** `_expires` 에 있으므로, 정리(`sweep`)할 때 만료 키만 훑으면 됩니다. 만료 없는 키가 100만 개여도 정리 비용은 그대로입니다.

### 3-2. 시계 — `time.monotonic` 과 `clock` 매개변수

- `time.time()` 은 "지금 몇 시" 라서 컴퓨터 시계를 바꾸면(NTP 보정, 사람이 수동 변경) 뒤로 갈 수도 있습니다. 그러면 만료가 갑자기 앞당겨지거나 늦어집니다.
- `time.monotonic()` 은 "어떤 기준점부터 흐른 초" 라서 **절대 뒤로 가지 않습니다.** 만료 계산에 알맞습니다.
- `clock` 을 매개변수로 받는 이유는 **테스트** 때문입니다. 60초 만료를 확인하려고 진짜 60초를 기다릴 수는 없습니다. 테스트는 `advance(60)` 하면 시간이 흐르는 가짜 시계를 넣습니다.

```python
clock = FakeClock()            # now = 1000.0
r = MiniRedis(clock=clock)
r.set("a", 1, ttl=1)
clock.advance(1)               # 1초 흐름 (실제로는 기다리지 않음)
r.get("a")                     # None — 만료
```

### 3-3. 저장 `set(key, value, ttl=None)` (`store.py:52`)

```python
if ttl is not None:
    _check_ttl(ttl)                       # ① 락 밖에서 먼저 검사
with self._lock:                          # ② 락
    self._data.set(key, value)            # ③ 값 저장
    if ttl is None:
        self._expires.delete(key)         # ④-a ttl 없음 → 기존 만료 지움
    else:
        self._expires.set(key, self._clock() + ttl)   # ④-b 만료 시각 = 지금 + ttl
    return True
```

- ① 을 락 밖에서 하는 이유: 틀린 ttl 이면 **아무것도 바꾸지 않고** 바로 `ValueError` 를 냅니다. 락을 잡을 필요도 없습니다.
- ④-a 는 실제 Redis `SET` 규칙입니다: ttl 없이 덮어쓰면 기존 만료가 사라집니다. (60초 뒤 사라질 값을 ttl 없이 다시 저장하면 영원히 남음)

### 3-4. 지연 삭제 — `_alive(key)` (`store.py:125`)

```python
def _alive(self, key):
    if key not in self._data:
        return False
    expire_at = self._expires.get(key)
    if expire_at is not None and expire_at <= self._clock():
        self._remove(key)                  # 만료됐으면 그 자리에서 두 테이블 모두에서 지움
        return False
    return True
```

`get` · `get_with_ttl` · `delete` · `exists` · `expire` · `ttl` **여섯 명령이 모두 이 함수를 먼저 거칩니다.** 그래서 만료된 값은 어떤 명령으로도 절대 밖으로 나가지 않습니다.

- `<=` (같은 순간도 만료): ttl=1 로 저장하고 **정확히** 1초 뒤에는 이미 없어야 합니다. `<` 면 그 한 순간 살아 있게 됩니다.
- 이 방식은 실제 Redis 의 **lazy expiration** 과 같습니다. 만료 시각이 됐다고 바로 지우는 게 아니라, 누가 볼 때 지웁니다.

### 3-5. 주기 삭제 — `sweep()` (`store.py:106`)

지연 삭제만 있으면, **아무도 다시 읽지 않는 만료 키는 메모리에 영원히 남습니다.** 그래서 서버가 1초마다 `sweep()` 을 부릅니다.

```python
def sweep(self):
    with self._lock:
        now = self._clock()                   # 기준 시각을 한 번만 읽음
        removed = 0
        for key in self._expires.keys():      # 만료가 있는 키만, 복사본으로
            if self._expires.get(key) <= now:
                self._remove(key)
                removed += 1
        return removed
```

- `now` 를 한 번만 읽는 이유: 도는 동안 시간이 흘러도 "같은 기준" 으로 판단하기 위해서입니다.
- `keys()` 가 복사본이라 돌면서 지워도 안전합니다 (2-6).
- **한계**: 만료 키를 전부 훑습니다(O(만료 키 수)). 실제 Redis 는 무작위로 20개만 뽑아 검사하고, 만료된 비율이 높으면 다시 뽑습니다. 만료 키가 수십만 개가 되면 그렇게 바꿔야 합니다 (코드에 `shortcut:` 주석).

| 방법 | 언제 | 없으면 생기는 문제 |
|---|---|---|
| 지연 삭제 `_alive` | 명령이 키를 볼 때마다 | `sweep` 사이(최대 1초) 동안 만료된 값이 응답으로 나감 |
| 주기 삭제 `sweep` | 1초마다 | 아무도 안 읽는 만료 키가 메모리를 계속 차지 |

### 3-6. 남은 시간 `ttl(key)` — Redis 규칙 -1 / -2 와 올림

| 상황 | 반환 |
|---|---|
| 키 없음 (또는 만료됨) | `-2` |
| 키는 있는데 만료 없음 | `-1` |
| 만료 있음 | 남은 초, **올림** |

```python
def _ttl_left(self, key):                                     # store.py:136
    expire_at = self._expires.get(key)
    return -1 if expire_at is None else math.ceil(expire_at - self._clock())
```

**왜 올림인가**: 0.3초 남은 키는 아직 살아 있습니다. 내림이면 `0` 이 나와서 "곧 사라짐" 인지 "없음" 인지 헷갈립니다. 올림이면 살아 있는 키는 항상 1 이상입니다 (`math.ceil(0.3) = 1`).
`_alive` 를 통과한 뒤에만 부르므로 남은 시간은 항상 0 보다 큽니다.

### 3-7. 값과 ttl 한 번에 — `get_with_ttl(key)` (`store.py:71`)

서버의 `GET /keys/{key}` 는 값과 ttl 을 함께 돌려줍니다. 이걸 `get()` 과 `ttl()` 을 따로 불러 만들면:

```
스레드 A: get("a")  → "값"
                         스레드 B: delete("a")
스레드 A: ttl("a")  → -2
→ 응답: {"value": "값", "ttl": -2}   ← "값은 있는데 키는 없다" 는 모순
```

`get_with_ttl` 은 **락 하나 안에서** 둘을 함께 읽어 이런 어긋난 조합이 나올 수 없습니다. 키가 없으면 `(None, -2)`.

### 3-8. ttl 입력 검사 — `_check_ttl` (`store.py:148`)

```python
MIN_TTL = 0.001

def _check_ttl(ttl):
    valid = not isinstance(ttl, bool) and isinstance(ttl, (int, float))
    try:
        valid = valid and math.isfinite(ttl) and ttl >= MIN_TTL
    except OverflowError:
        valid = False
    if not valid:
        raise ValueError(f"ttl은 {MIN_TTL}초 이상의 유한한 숫자여야 합니다")
```

| 입력 | 결과 | 이유 |
|---|---|---|
| `60` · `1.5` · `0.001` | 통과 | 정수 · 소수 모두 (최소 1ms) |
| `0` · `-1` · `0.0001` | 거부 | 1ms 미만 |
| `True` | 거부 | `True` 는 `int` 의 한 종류라 그냥 두면 1초로 들어감 |
| `float("nan")` · `float("inf")` | 거부 | `isfinite` |
| `"5"` · `None` · `[]` | 거부 | 숫자가 아님 |
| `10**400` | 거부 | 너무 큰 정수는 float 로 못 바꿔 `isfinite` 가 `OverflowError` → 잡아서 거부 |

**왜 최소 1ms 인가**: 부동소수점은 큰 수에 아주 작은 수를 더하면 사라집니다. 실제로 `1000.0 + 1e-14 == 1000.0` 은 `True` 입니다. 그러면 "지금 + ttl" 이 "지금" 과 같아져 저장하자마자 만료됩니다. 1ms(`1000.0 + 0.001 = 1000.001`)는 안전합니다. 실제 Redis 의 `PEXPIRE` 도 1ms 단위입니다.

### 3-9. 동시성 — 락 하나

HTTP 서버는 요청마다 스레드가 따로 돌고, 정리 스레드도 동시에 돕니다. 락이 없으면 이런 일이 생깁니다:

```
스레드 A: set("x")  → 7번째 항목 → 리사이즈 시작 (새 칸 16개를 만드는 중)
스레드 B: set("y")  → 아직 옛 8칸에 "y" 를 붙임
스레드 A: 리사이즈 끝 → self._buckets = 새 16칸   ← "y" 가 사라짐
```

그래서 `MiniRedis` 의 **공개 메서드 9개는 모두 `with self._lock:` 안에서만** 해시 테이블을 만집니다. 한 번에 명령 하나만 실행됩니다.

- 특히 "확인한 뒤 쓰는" 동작이 위험합니다: "만료됐나? → 지우기", "키 있나? → 만료 설정", "같은 키 있나? → 갱신 / 없으면 삽입 + 리사이즈".
- 실제 Redis 도 명령을 **한 스레드에서 하나씩** 처리합니다. 효과가 같습니다.
- 명령 하나는 마이크로초 단위라, HTTP 처리 시간(밀리초)에 비하면 줄 서는 시간은 무시할 수 있습니다.
- `HashTable` 자체에는 락이 없습니다. 혼자 쓸 때는 필요 없고, 동시성은 위 계층의 책임으로 나눴습니다.
- 내부 함수(`_alive` · `_ttl_left` · `_remove`)는 **락을 잡은 상태에서만** 부릅니다. 안에서 또 락을 잡으면 `threading.Lock` 은 재진입이 안 되어 멈춰 버립니다.

| 메서드 | 반환 | 만료된 키 |
|---|---|---|
| `set(key, value, ttl=None)` | `True` | — |
| `get(key)` | 값 / `None` | `None` |
| `get_with_ttl(key)` | `(값, ttl)` / `(None, -2)` | `(None, -2)` |

### 3-11. 서버를 꺼도 데이터 지키기 — 스냅샷 (`persistence.py`)

메모리에만 있는 데이터는 서버를 끄면 사라집니다. 실제 Redis 의 **RDB** 처럼, 저장소 전체를 가끔 파일 하나에 찍어 두고 켤 때 되살립니다. 이 파일은 김건희 님 브랜치의 구현을 그대로 써서 팀과 파일 형식이 같습니다.

**① 한 시점의 사진 찍기 — `MiniRedis.dump()`**

```python
def dump(self):
    with self._lock:                                  # 락 하나 안에서 한 번에
        now = self._clock()
        entries = []
        for key in self._data.keys():
            expire_at = self._expires.get(key)
            if expire_at is not None and expire_at <= now:
                continue                              # 이미 만료된 키는 빼고
            entries.append((key, self._data.get(key), None if expire_at is None else expire_at - now))
        return entries
```

락 안에서 한 번에 모으므로, 저장 도중 다른 요청이 끼어들어도 "어떤 키는 수정 전, 어떤 키는 수정 후" 가 섞이지 않습니다. 남은 시간은 **올림하지 않은 그대로**(`27.4`) 둡니다 — 복구할 때 정확히 빼야 하니까요.

**② 파일에 쓰기 — `save_snapshot`**

```json
{"format": 1, "saved_at": 1794490976.3, "entries": [{"key": "user:1", "value": {"name": "철수"}, "ttl": null},
                                                    {"key": "session", "value": "s", "ttl": 27.4}]}
```

- `saved_at` 은 **벽시계**(`time.time()`) 입니다. 저장소가 쓰는 `monotonic` 은 컴퓨터를 다시 켜면 0 부터 다시 세서, 파일에 남기면 의미가 없습니다.
- **원자적 교체**: `dump.json.tmp` 에 끝까지 쓰고 → `fsync` 로 디스크에 확실히 내리고 → `os.replace` 로 이름을 바꿉니다. 같은 폴더 안의 이름 바꾸기는 한 번에 일어나므로, 저장 도중 전원이 나가도 `dump.json` 은 "이전 것" 이거나 "새 것" 이지 반쯤 쓰인 파일이 되지 않습니다. 쓰다가 실패하면 `.tmp` 만 지웁니다.

**③ 되살리기 — `load_snapshot`**

1. 파일이 없으면 0 (처음 켜는 서버).
2. JSON 을 읽고 `format` · `saved_at` · 모든 항목의 키 · ttl 을 **먼저 전부 검사**합니다. 하나라도 이상하면 `SnapshotError` — 저장소에는 아무것도 넣지 않습니다 (일부만 복구된 어정쩡한 상태가 없게).
3. **꺼져 있던 시간** = 지금 벽시계 − `saved_at` (시계가 뒤로 갔으면 0). 각 ttl 에서 이만큼 뺍니다. 0.001초 미만이 되면 꺼져 있는 동안 만료된 것이라 건너뜁니다.
4. `store.set(key, value, ttl)` 로 넣습니다 — 평소 저장과 같은 길이라 ttl 규칙도 그대로 적용됩니다.

**④ 언제 저장하나 — `start_periodic_snapshot` + 서버 `main()`**

```
켤 때     load_snapshot  → "[snapshot] data/dump.json에서 키 3개 복구"
         (파일이 손상됐으면 SystemExit — 빈 서버로 떠서 그 파일을 덮어쓰지 않게)
도는 중   60초마다 save_snapshot (실패해도 서버는 계속, 다음 주기에 다시)
끌 때     Ctrl+C → 서버 닫기 → 정리 스레드 멈추고 마지막으로 한 번 더 저장
```

실제로 확인한 것: 키 3개(ttl 없음 · ttl 30 · ttl 0.5)를 넣고 1초 주기 저장 → 파일에 0.5초짜리는 빠져 있음 → 종료 직전 키 하나 더 → Ctrl+C → 3초 뒤 다시 켬 → 키 3개 복구, ttl 30 짜리는 **27** 로 줄어 있음 → 손상된 파일로 켜면 종료 코드 1 이고 파일은 그대로.

**한계**: 스냅샷 사이(최대 60초)에 서버가 갑자기 죽으면(전원 · `kill -9`) 그 사이 변경은 잃습니다. 명령마다 기록하는 AOF 는 이 손실이 작지만 파일이 커집니다. Mini Redis 는 주로 캐시라 잃은 데이터는 원본에서 다시 가져오면 되므로 스냅샷을 택했습니다.

### 4-1. 파이썬 `http.server` 의 구조

### 4-2. 모든 응답은 `_handle` 한 곳에서 (`server.py:79`)

```python
def _handle(self, method):
    try:
        status, body = self._route(method)
    except ApiError as e:                       # 예상한 오류 (400 · 404 · 405 · 408 · 413)
        status, body = e.status, {"error": str(e)}
    except Exception:                           # 예상 못 한 오류
        status, body = 500, {"error": "서버 내부 오류"}
    self._send(status, body)
```

- `do_GET` · `do_PUT` · `do_DELETE` · `do_POST` · `do_PATCH` · `do_OPTIONS` 가 전부 여기로 옵니다.
- `PATCH` · `OPTIONS` 까지 받는 이유: 표준 라이브러리는 모르는 메서드에 **HTML** 501 페이지로 답합니다. "모든 응답은 JSON" 이라는 약속을 지키려고 받아서 405 JSON 으로 답합니다.
- 처리 중 어디서든 `raise ApiError(404, "키가 없습니다")` 하면 그대로 응답이 됩니다. 오류 처리 코드가 흩어지지 않습니다.
- 예상 못 한 오류가 나도 그 요청만 500 으로 끝나고 **서버는 계속 돕니다.**

### 4-3. 라우팅 — 경로를 나눈 뒤 디코딩 (`server.py:89`)

```python
path = self.path.split("?", 1)[0]                         # 쿼리(?x=1) 버림
parts = [unquote(p) for p in path.split("/")[1:]]         # 먼저 "/" 로 나누고, 조각마다 디코딩
```

**왜 "나눈 뒤 디코딩" 인가**: 키 `메이플/a` 는 URL 에서 `%EB%A9%94%EC%9D%B4%ED%94%8C%2Fa` 로 옵니다. 먼저 디코딩하면 `/keys/메이플/a` 가 되어 `/` 로 나눌 때 키가 둘로 쪼개집니다. 먼저 나누고 조각마다 디코딩하면 `["keys", "메이플/a"]` 로 키가 온전합니다.

```
/keys/user:1                    → ["keys", "user:1"]          → 키 하나짜리 (GET · PUT · DELETE)
/keys/user:1/ttl                → ["keys", "user:1", "ttl"]   → 남은 시간 (GET)
/keys/user:1/expire             → ["keys", "user:1", "expire"]→ 만료 설정 (POST)
/health                         → ["health"]                  → 상태 확인 (GET)
/keys/                          → ["keys", ""]                → 빈 키 → 404
/keys/a/b/c · /nope             →                              → 404
```

경로는 맞는데 메서드가 다르면 405 이고, 문구가 그 경로가 받는 메서드를 알려 줍니다: `/keys/{key}` 는 `"GET / PUT / DELETE만 지원합니다"`, `/ttl` · `/health` 는 `"GET만 지원합니다"`, `/expire` 는 `"POST만 지원합니다"`.

### 4-4. 입력 검사 — 신뢰 경계 (`_read_json`, `server.py:142`)

서버는 **밖에서 오는 요청을 처음 받는 곳**입니다. 무엇이든 올 수 있으므로 저장소에 넘기기 전에 여기서 막습니다. 검사 순서:

| 순서 | 검사 | 실패 시 |
|---|---|---|
| 1 | `Content-Length` 가 있고 ASCII 숫자인가 | 400 `Content-Length가 올바르지 않습니다` |
| 2 | 1MB 이하인가 | 413 `요청 본문이 너무 큽니다 (최대 1MB)` (4-5) |
| 3 | 10초 안에 다 받았나 | 408 `요청 본문을 제한 시간 안에 다 받지 못했습니다` |
| 4 | 올바른 JSON 인가 (`NaN` · `Infinity` 거부) | 400 `본문이 올바른 JSON이 아닙니다 (NaN / Infinity 불가)` |
| 5 | JSON **객체** `{...}` 인가 | 400 `본문은 JSON 객체({...})여야 합니다` |
| 6 | 응답으로 다시 쓸 수 있나 (한 번 써 봄) | 400 `JSON이 너무 깊게 중첩되어 있습니다` / `UTF-8로 표현할 수 없는 문자(짝 없는 서로게이트)가 들어 있습니다` |
| 7 | `value` 가 있고 `null` 이 아닌가 (PUT) / `ttl` 이 있나 (expire) | 400 `value가 필요합니다 (null은 저장할 수 없습니다)` / `ttl이 필요합니다` |
| 8 | ttl 규칙 (`store._check_ttl`) | 400 `ttl은 0.001초 이상의 유한한 숫자여야 합니다` |

**하나씩 이유**
- **1 — `isascii()`**: `"²"`(위첨자 2)는 `isdigit()` 은 `True` 인데 `int()` 는 실패합니다. 그대로 두면 500 이 납니다.
- **4 — `NaN` 거부**: 파이썬 `json` 은 `NaN` · `Infinity` 를 받아 주지만 **표준 JSON 이 아닙니다.** 저장했다가 응답으로 내보내면 다른 언어 클라이언트가 읽지 못합니다. `parse_constant` 로 들어오는 순간 거부합니다.
- **6 — "한 번 써 보기"**: 검증 중 발견한 문제입니다. Python 3.14 는 `[[[[…]]]]` 처럼 10만 단계 중첩된 JSON 을 **읽기는 하는데**, 응답으로 다시 쓸 때 `RecursionError` 가 납니다. 짝 없는 반쪽 문자 `"\ud800"` 도 JSON 문법으로는 통과하지만 UTF-8 로 못 바꿉니다. 그대로 두면 "저장은 성공, 조회는 500 · 끊김" 이 됩니다. 그래서 **저장하기 전에 `json.dumps(...).encode("utf-8")` 를 한 번 해 보고** 안 되면 거부합니다.
- **7 — `null` 거부**: `null` 을 저장하면 조회 때 `None` 이 나와 "키 없음(404)" 과 구별이 안 됩니다. 그래서 서버에서 GET 의 `None` = "없거나 만료됨" 이 확실해집니다.
- **8 — ttl 규칙은 한 곳에만**: 서버는 ttl 을 직접 검사하지 않고 저장소가 내는 `ValueError` 를 400 으로 바꿉니다(`_call`, `:135`). 규칙을 두 곳에 두면 언젠가 서로 달라집니다.

### 4-5. 413 을 보낼 때 본문을 읽어서 버리는 이유 (`_discard`, `server.py:177`)

1MB 를 넘는 본문이 오면, 읽지 않고 바로 413 을 보내고 연결을 닫으면 될 것 같습니다. 그런데 실제로 그렇게 하면:

```
클라이언트: 본문 2MB 를 보내는 중 …
서버:       헤더만 보고 413 응답 → 연결 닫음 (본문은 수신 버퍼에 남아 있음)
운영체제:   "읽지 않은 데이터가 남은 채 닫혔다" → RST(강제 끊김) 전송
클라이언트: 413 응답을 읽기도 전에 "Connection reset by peer" 오류
```

dev 코드와 dev 테스트에서도 실패하던 문제입니다. 그래서 413 을 보내기 전에 남은 본문을 **최대 16MB 까지 64KB 씩 읽어서 버립니다.** 그러면 클라이언트는 정상적으로 413 응답을 받습니다.
보내다가 멈춘 클라이언트라면 제한 시간(10초)에서 멈추고 바로 413 을 보냅니다. 16MB 보다 큰 본문은 다 버리지 못하고 끊길 수 있습니다 (`shortcut:` 주석).

### 4-6. 408 — 보내다 멈춘 클라이언트 (`setup`, `server.py:55`)

`Content-Length: 100` 이라고 해 놓고 1바이트만 보낸 뒤 멈추는 클라이언트가 있으면, 서버 스레드는 나머지 99바이트를 **영원히** 기다립니다. 이런 연결이 쌓이면 서버가 멈춥니다. 그래서 연결마다 읽기 제한 시간(10초)을 걸고, 넘으면 408 로 끝냅니다.

```python
def setup(self):
    self.timeout = REQUEST_TIMEOUT       # 클래스 속성이 아니라, 연결마다 모듈 값을 읽는다
    super().setup()
```

클래스 속성 `timeout = REQUEST_TIMEOUT` 으로 두면 import 때 한 번만 읽혀서, 테스트가 `REQUEST_TIMEOUT = 0.5` 로 바꿔도 적용되지 않습니다. dev 테스트가 이렇게 바꿔서 시험하므로 연결마다 읽게 했습니다.

### 4-7. 연결 대기열 128 (`server.py:213`)

```python

    request_queue_size = 128
```

운영체제는 서버가 아직 받지 못한 연결을 **대기열**(listen backlog)에 줄 세워 둡니다. 표준 라이브러리 기본값은 **5** 입니다.
검증 중 클라이언트 20개로 부하 검사를 했더니 요청 1만 개 중 **3,869개가 `Connection reset`** 으로 끊겼습니다. 대기열 5칸이 넘치자 macOS 가 넘친 연결을 강제로 끊은 것입니다. 128 로 늘린 뒤 오류 0개가 됐고, 50개 동시 접속 테스트(`test_many_simultaneous_connections`)를 회귀 테스트로 넣었습니다. (고치기 전 코드에서는 세 번 모두 실패, 고친 뒤 다섯 번 모두 통과)

### 4-8. 응답 보내기 (`_send`, `server.py:188`)

```python

    data = json.dumps(body, ensure_ascii=False).encode("utf-8")   # 한글을 글자 그대로
except UnicodeEncodeError:
    data = json.dumps(body).encode("ascii")                        # 못 바꾸는 값만 \uXXXX 로
```

- `ensure_ascii=False`: 한글이 `메이플` 가 아니라 `메이플` 로 보입니다.
- HTTP 로는 반쪽 문자를 막았지만, 파이썬 코드로 저장소에 **직접** 넣은 값은 막을 수 없습니다. 그런 값도 응답이 끊기지 않게, 그때만 모든 비ASCII 를 `\uXXXX` 로 적습니다 (그래도 올바른 JSON).

- `log_message` 를 비워 요청마다 콘솔에 찍지 않습니다 (성능 측정에 출력 비용이 섞이지 않게).

### 4-9. 주기 삭제 스레드 (`server.py:215`)

```python
def __init__(self, store, address):
    super().__init__(address, Handler)
    self.store = store
    self._stop = threading.Event()
    threading.Thread(target=self._sweep_loop, daemon=True).start()

def _sweep_loop(self):
    while not self._stop.wait(SWEEP_INTERVAL):    # 1초 기다리다가, stop 이 켜지면 바로 깨어나 끝
        self.store.sweep()

def server_close(self):
    self._stop.set()
    super().server_close()
```

- `time.sleep(1)` 대신 `Event.wait(1)` 을 쓰는 이유: 서버를 닫을 때 최대 1초를 기다리지 않고 **바로** 멈출 수 있습니다.
- `daemon=True`: 프로그램이 끝날 때 이 스레드 때문에 종료가 막히지 않습니다.

### 4-10. 실행 (`main`, `server.py:237`)

- 기본 주소 `127.0.0.1` — 같은 컴퓨터에서만 접속됩니다. 인증이 없는 저장소라 외부에 열지 않는 것이 기본입니다 (`--host 0.0.0.0` 으로 열 수 있음).
- `port=0` 이면 운영체제가 빈 포트를 고릅니다. 테스트가 이걸로 서로 부딪히지 않게 서버를 띄웁니다.
- Ctrl+C 를 누르면 `server_close()` 로 정리 스레드까지 멈춥니다.

## 5. 캐시 데모 — `demo/`

### 5-1. Cache-Aside 패턴

```
GET /items/1
  │
  ├─ Mini Redis 에 "item:1:v1" 있나? ── 있음 ──→ 바로 응답          "cache": "HIT"   (수 ms)
  │
  └─ 없음 → 느린 원본 조회 (0.2초) → Mini Redis 에 60초 저장 → 응답   "cache": "MISS"  (약 200ms)
```

애플리케이션(데모 API)이 캐시를 직접 보고, 없으면 채웁니다. 이게 가장 흔한 캐시 사용법입니다.
`demo/api_server.py` 는 dev(김건희 님) 파일을 그대로 씁니다. 데모 API 는 Mini Redis 를 import 하지 않고 **HTTP 로만** 씁니다(`RedisClient` 클래스). 진짜 Redis 를 쓰는 서비스와 같은 모양입니다.

### 5-2. 무효화 — 왜 버전 키인가

가격을 바꾸면 캐시의 옛 가격을 없애야 합니다(무효화). 가장 단순한 방법은 "원본 수정 → 캐시 삭제" 인데, 이런 경쟁 상태가 생깁니다:

```
시간 →
요청 A (GET)  : 원본에서 가격 100 읽음 ─────── (0.2초 걸림) ─────── 캐시에 100 저장!
요청 B (PUT)  :            가격을 5 로 수정 → 캐시 삭제
결과          : 이후 60초 동안 옛 가격 100 이 HIT 로 나감
```

데모는 **버전 키**로 막습니다.

- 원본 아이템마다 `version` 이 있고, 수정할 때마다 1 오릅니다.
- 캐시 키는 `item:{id}:v{version}` 입니다.
- 읽기는 **지금 버전의 키**만 봅니다. 수정으로 버전이 v2 가 되면, v1 키는 그 순간부터 아무도 읽지 않습니다 → 무효화 완료.
- 위 경쟁 상태에서 요청 A 의 옛 데이터(v1)는 v1 키로만 갑니다. 게다가 저장 직전에 "읽은 버전 == 지금 버전?" 을 확인해, 이미 옛 버전이면 **저장 자체를 하지 않습니다.**
- 옛 키 삭제는 메모리 정리용이고, 결과를 `"old_cache_deleted": true/false` 로 돌려줍니다. 못 지워도 60초 뒤 만료됩니다.
- `fetch_item` 은 실제 DB 처럼 **읽은 뒤에 기다립니다**(읽은 데이터가 늦게 도착). 그래서 위 경쟁 상태를 테스트로 실제로 만들어 확인할 수 있습니다.

### 5-3. 캐시가 고장 나도 서비스는 돈다 — BYPASS

Mini Redis 가 꺼져 있거나, 1초 안에 답이 없거나, 이상한 응답(JSON 아님 · `value` 없음)을 주거나, 저장이 실패하면 **원본으로라도 응답**합니다 (`"cache": "BYPASS"`).
캐시는 빠르게 하려고 쓰는 것이지, 없으면 서비스가 멈추는 것이 아니어야 합니다. 모든 실패는 `RedisUnavailable` 예외 하나로 모아 처리합니다.

### 5-4. 데모 API 정리

| 요청 | 응답 |
|---|---|
| `GET /items/{id}` | `{"item": {...}, "cache": "HIT" \| "MISS" \| "BYPASS"}` |
| `GET /items/{id}?cache=off` | 매번 원본, `"cache": "OFF"` |
| `PUT /items/{id}` body `{"price": 숫자}` | `{"item": {...}, "old_cache_deleted": bool}` |
| 없는 아이템 · 잘못된 경로 | 404 |
| 잘못된 가격(`NaN` · 문자열 · 불리언 등) | 400 |

### 5-5. 벤치마크 — `benchmark.py`

```python
def measure(url, n):
    total = 0.0
    for _ in range(n):
        start = time.perf_counter()
        with urlopen(url, timeout=10) as res:
            res.read()                         # 본문까지 다 받은 시간을 잰다
        total += time.perf_counter() - start
    return total / n * 1000                    # 평균 ms
```

- `time.perf_counter()`: 짧은 시간을 재는 데 가장 정밀한 시계입니다.
- 본문까지 다 읽는 이유: 헤더만 받고 끝내면 서버가 덜 일한 것처럼 보입니다.
- `python -m demo.benchmark` 만 치면 Mini Redis 서버와 데모 서버를 **프로그램 안에서 빈 포트로 띄워** 잽니다. 명령 하나로 끝납니다.

| 방식 (같은 아이템 20번) | 평균 응답 시간 |
|---|---|
| 캐시 미사용 (`?cache=off`) | 204.58ms (원본 200ms + HTTP 약 5ms) |
| 캐시 사용 (첫 요청 MISS 포함) | 11.32ms |

약 **18배** 빠릅니다. 캐시 사용 평균에는 첫 MISS(약 200ms)가 1/20 섞여 있어서, HIT 만 보면 수 ms 입니다.

## 7. 자주 나올 질문

**Q. 왜 파이썬 `dict` 를 안 썼나요?**
과제 규칙입니다. 해시 테이블이 어떻게 동작하는지(해시 · 충돌 · 리사이즈)를 직접 만들어 보는 게 목적입니다. 데모의 "느린 원본" 은 Mini Redis 가 아니라 DB 흉내라서 `dict` 를 씁니다.

**Q. 해시 테이블이 정말 O(1) 인가요?**
평균적으로 그렇습니다. 부하율을 0.75 이하로 지키면 한 칸에 평균 1개 미만이 들어갑니다. 모든 키가 한 칸에 몰리는 최악의 경우는 O(n) 이지만, FNV-1a 가 키를 고르게 퍼뜨려 실제로는 거의 일어나지 않습니다.

**Q. 리사이즈할 때 왜 모든 항목을 다시 넣나요?**
칸 번호 = `해시 % 칸 수` 입니다. 칸 수가 8 → 16 으로 바뀌면 같은 키도 칸 번호가 바뀝니다 (`user:1` 은 3 → 11). 옛 번호에 두면 찾지 못합니다.

**Q. 만료된 키는 언제 지워지나요?**
두 번 기회가 있습니다. 누가 그 키를 보는 순간(지연 삭제), 그리고 1초마다 도는 정리(주기 삭제). 그래서 만료된 값은 응답으로 나가지 않고, 메모리에도 최대 약 1초만 남습니다.

**Q. 락이 하나면 느리지 않나요?**
명령 하나는 해시 테이블 접근 몇 번이라 마이크로초 단위입니다. HTTP 요청 하나를 처리하는 데 드는 시간(밀리초)에 비하면 아주 작습니다. 실제 Redis 도 명령을 한 스레드에서 하나씩 처리합니다. 초당 수만 요청이 되면 칸 범위별로 락을 나누는 방법이 있습니다.

**Q. ttl 은 왜 올림인가요?**
살아 있는 키가 `0` 을 돌려주면 "없음" 과 헷갈립니다. 0.3초 남은 키는 `1` 입니다.

**Q. `null` 은 왜 저장할 수 없나요?**
조회 결과 `None` 이 "값이 null" 인지 "키가 없음" 인지 구별할 수 없어서입니다. 막아 두면 GET 에서 `None` 은 언제나 404 입니다.

**Q. 왜 HTTP 인가요? 진짜 Redis 는 RESP 라던데요.**
팀 뼈대가 HTTP JSON API 로 정했습니다. curl · 브라우저 · 어떤 언어로든 바로 쓸 수 있어 시연과 테스트가 쉽습니다.

**Q. 서버를 끄면 데이터는요?**
남습니다. 60초마다 + 끌 때 `data/dump.json` 에 스냅샷을 저장하고, 켤 때 복구합니다. ttl 은 꺼져 있던 시간만큼 줄어서 돌아옵니다. 다만 전원이 나가는 식으로 갑자기 죽으면 마지막 저장 뒤 최대 60초치 변경은 잃습니다 (3-11).

**Q. 실제 Redis 와 무엇이 같고 무엇이 다른가요?**

| | 같음 | 다름 |
|---|---|---|
| 만료 | 지연 삭제 + 주기 삭제, ttl -1 / -2, SET 이 만료를 지움, 최소 1ms | Redis 는 주기 삭제 때 무작위 20개 표본 검사 |
| 동시성 | 명령을 한 번에 하나씩 | Redis 는 단일 스레드 이벤트 루프, 여기는 락 |
| 자료형 | 문자열 키 | Redis 는 List · Set · Hash · Sorted Set 등 |
| 통신 | — | Redis 는 RESP, 여기는 HTTP JSON |
| 메모리 · 영속성 | 스냅샷(RDB 방식) 저장 · 복구 | Redis 는 메모리 한도 · LRU 제거 · AOF(명령 기록)도 있음 |

## 8. 용어 사전

| 용어 | 뜻 |
|---|---|
| 해시 함수 | 키를 정해진 크기의 숫자로 바꾸는 함수. 같은 키는 언제나 같은 숫자 |
| 버킷(칸) | 해시 테이블 배열의 한 자리. 여기서는 리스트 하나 |
| 충돌 | 다른 키가 같은 칸에 오는 것 |
| 체이닝 (Separate Chaining) | 충돌한 항목을 같은 칸의 리스트에 줄 세우는 방법 |
| 개방 주소법 | 충돌하면 옆 칸 등 다른 빈 칸을 찾아 넣는 방법 (여기서는 안 씀) |
| 부하율 (load factor) | 항목 수 ÷ 칸 수. 높을수록 느려짐 |
| 리사이즈 | 칸 수를 늘리고 모든 항목을 새 칸 번호로 다시 넣는 것 |
| FNV-1a | XOR 과 곱하기를 바이트마다 반복하는 단순하고 빠른 해시 함수 |
| TTL (Time To Live) | 값이 살아 있는 시간. 지나면 만료 |
| 지연 삭제 (lazy expiration) | 만료 키를 누가 볼 때 지우는 방식 |
| 주기 삭제 (active expiration) | 일정 간격으로 만료 키를 찾아 지우는 방식 |
| 락 (Lock) | 한 번에 한 스레드만 들어가게 막는 장치 |
| 경쟁 상태 (race condition) | 여러 스레드 · 요청의 실행 순서에 따라 결과가 틀려지는 상황 |
| 신뢰 경계 | 밖에서 오는 입력을 처음 받는 곳. 여기서 검사해야 안쪽이 안전 |
| Cache-Aside | 애플리케이션이 캐시를 먼저 보고, 없으면 원본을 읽어 캐시를 채우는 방식 |
| 캐시 무효화 | 원본이 바뀌었을 때 캐시의 옛 값을 못 쓰게 하는 것 |
| 버전 키 | 캐시 키에 데이터 버전을 넣어, 버전이 바뀌면 옛 키를 자연히 안 읽게 하는 무효화 방법 |
| HIT / MISS / BYPASS | 캐시에 있음 / 없어서 원본 조회 / 캐시 고장이라 원본만 조회 |
| listen backlog | 운영체제가 아직 받지 않은 연결을 줄 세워 두는 대기열 |
| RST | TCP 연결을 강제로 끊는 신호. 클라이언트에는 `Connection reset` 으로 보임 |
| monotonic 시계 | 절대 뒤로 가지 않는 시계. 시간 간격 계산용 |
| 회귀 테스트 | 고친 버그가 다시 생기지 않는지 확인하는 테스트 |
| 스냅샷 (RDB) | 저장소 전체를 가끔 파일 하나에 찍어 두는 영속성 방식. 실제 Redis 의 RDB |
| AOF | 명령마다 파일 끝에 기록하는 영속성 방식 (여기서는 안 씀) |
| 원자적 교체 | 임시 파일에 다 쓴 뒤 이름 바꾸기 한 번으로 바꿔치기 — 반쯤 쓰인 파일이 생기지 않음 |
