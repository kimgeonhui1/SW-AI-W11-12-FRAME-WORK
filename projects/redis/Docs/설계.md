# Mini Redis 설계 

> 작성 2026-11-12 · 언어 Python 3 (표준 라이브러리만) · 팀 뼈대 `25c050c` 의 파일 · 함수 · 매개변수 이름을 그대로 따른다
> 동작과 오류 문구는 dev(김건희 님 구현)와 맞췄다 — dev 의 테스트 61개가 이 코드에서 그대로 전부 통과한다. `demo/api_server.py` 는 dev 파일을 그대로 쓴다

## 1. 전체 아키텍처

```
 Client (demo/api_server.py · demo/benchmark.py · curl)
   │  HTTP JSON
   ▼
 API Server ─── mini_redis/server.py      요청 읽기 · 입력 검사 · JSON 응답
   │  메서드 호출
   ▼
 Command Layer ─ mini_redis/store.py      MiniRedis: 만료(TTL) · 락 · 명령 실행
   │  get / set / delete / keys
   ▼
 Storage Engine ─ mini_redis/hashtable.py HashTable: 키 → 값 저장 (dict 사용 X)

 (선택) mini_redis/persistence.py         스냅샷 파일 저장 · 복구 (60초마다 + 종료 때, 켤 때 복구)
```

| 계층 | 파일 | 담당 역할 | 모르는 것 |
|---|---|---|---|
| Client | `demo/` | 요청 전송, 캐시 활용, 성능 측정 | 저장 방식 |
| API Server | `server.py` | HTTP 경로 → 메서드 호출, 입력 검사, 상태 코드 | 해시 테이블 |
| Command Layer | `store.py` | 만료 처리, 동시성 제어, Redis 규칙(-1 / -2) | HTTP |
| Storage Engine | `hashtable.py` | 해시 · 충돌 처리 · 리사이즈 | 만료 · 락 |

- 아래 계층은 위 계층을 모른다. 그래서 `HashTable` 은 만료를 모르고, `MiniRedis` 는 HTTP를 모른다.
- 각 계층을 따로 테스트할 수 있다 (`test_hashtable` → `test_store` → `test_server`).

## 2. 핵심 데이터 구조

### 2-1. 해시 테이블 (Storage Engine)

```
buckets (리스트, 처음 8칸)
├── [0] []                                    ← 빈 칸
├── [1] [ ["user:1", 항목], ["post:9", 항목] ] ← 충돌: 같은 칸에 줄 세움 (체이닝)
├── [2] [ ["name", 항목] ]
├── ...
└── [7] []
```

- 칸(bucket) = 파이썬 리스트, 칸 안의 항목 = `[key, value]` 리스트 (값을 바꿀 수 있게 튜플이 아닌 리스트).
- `size` = 저장된 항목 수 (`__len__` 이 그대로 돌려준다 → O(1)).

### 2-2. 저장 항목 (Command Layer)

`MiniRedis` 는 해시 테이블 **두 개**를 쓴다 (dev 와 같은 구조, 실제 Redis 도 값과 만료 시각을 따로 둔다).

```python
_data    : HashTable   # 키 → value        예: "user:1" → "Nameisme"
_expires : HashTable   # 키 → expire_at    ttl 을 준 키만. 예: "hi" → 12345.67
```

- 만료가 있는 키만 `_expires` 에 있으므로 `sweep()` 은 만료 키만 훑는다.

| 필드 | 뜻 |
|---|---|
| `key` | 데이터 식별자 (해시 테이블의 키, 문자열) |
| `value` | 실제 데이터 (JSON으로 표현되는 값: 문자열 · 숫자 · 불리언 · 리스트 · 객체). `MiniRedis` 는 `None` 도 받지만, HTTP 는 `null` 을 400 으로 거부한다 (8장) |
| `expire_at` | 만료 시각 `clock()` 기준 초 (기본 `time.monotonic`). 만료 없음 = `_expires` 에 키가 없음 |

- **시계는 `MiniRedis(clock=time.monotonic)` 매개변수** (dev 와 같음): `monotonic` 은 시스템 시계를 바꿔도(NTP 보정, 수동 변경) 만료가 앞당겨지거나 늦어지지 않는다. 테스트는 가짜 시계를 넣는다.
- 단, `monotonic` 값은 프로그램을 다시 켜면 의미가 없다 → 스냅샷에는 "남은 초" 와 저장 시각을 적고, 복구할 때 꺼져 있던 시간만큼 뺀다 (9장).

## 3. 핵심 함수 설계

### 3-1. `HashTable` (`hashtable.py`)

| 함수 | 역할 | 시간 |
|---|---|---|
| `__init__(capacity=8)` | 빈 칸 `capacity` 개 만들기. 1 이상의 정수가 아니면 `ValueError` | O(capacity) |
| `fnv1a(key)` *(모듈 함수)* | 키 → 64비트 정수 (FNV-1a, dev 와 같음). 문자열이 아니면 `TypeError` | O(키 길이) |
| `_index(key)` *(내부)* | `fnv1a(key) % 칸 수` → 칸 번호 | O(키 길이) |
| `_find(key)` *(내부)* | 칸에서 `[key, value]` 항목 찾기, 없으면 `None` | 평균 O(1) |
| `__contains__(key)` | `key in table` — `None` 값도 "있음" (`store.py` 가 사용) | 평균 O(1) |
| `get(key, default=None)` | 값 조회, 없으면 `default` | 평균 O(1) |
| `set(key, value)` | 저장 · 덮어쓰기, 부하율 초과 시 리사이즈 | 평균 O(1) |
| `delete(key)` | 삭제. 지웠으면 `True`, 없던 키면 `False` | 평균 O(1) |
| `keys()` | 모든 키 목록 (새 리스트) | O(n) |
| `__len__()` | 항목 수 | O(1) |
| `capacity()` | 지금 칸 수 (dev 와 같음, 리사이즈 확인용) | O(1) |
| `_resize(new_capacity)` *(내부)* | 칸을 늘리고 모든 항목 다시 배치 | O(n) |

### 3-2. `MiniRedis` (`store.py`)

| 함수 | 역할 | 반환 |
|---|---|---|
| `__init__(clock=time.monotonic)` | 해시 테이블 2개 + 락 준비. `clock` 은 테스트용 시계 (뼈대에 없던 선택 매개변수 — dev 와 같음) | — |
| `set(key, value, ttl=None)` | 저장 · 갱신. `ttl` 초 뒤 만료. **ttl 없이 덮어쓰면 기존 만료는 사라진다** (Redis SET 규칙) | `True` |
| `get(key)` | 조회. 없거나 만료면 `None` | 값 또는 `None` |
| `get_with_ttl(key)` | 값과 남은 ttl 을 락 하나 안에서 함께 조회 (서버 GET 이 사용 — 따로 읽으면 사이에 끼어든 요청 때문에 어긋남) | `(값, ttl)` / 없으면 `(None, -2)` |
| `delete(key)` | 삭제(무효화). 이미 만료된 키는 없는 것 | `True` / `False` |
| `exists(key)` | 키가 있는지 (만료 = 없음) | `True` / `False` |
| `expire(key, ttl)` | 있는 키에 만료 설정 | 키 없으면 `False` |
| `ttl(key)` | 남은 초 (올림). 만료 없음 `-1`, 키 없음 `-2` | 정수 |
| `sweep()` | 만료된 키를 전부 지움 | 지운 개수 |
| `__len__()` | 저장된 키 수 (아직 sweep 안 된 만료 키 포함, 서버 `/health` 가 사용) | 정수 |
| `_alive(key)` *(내부, 락 안에서만)* | 키가 살아 있으면 `True`. 만료됐으면 두 테이블에서 지운 뒤 `False` | `True` / `False` |

**`ttl` 입력 규칙** (`set` · `expire` 공통)
- `MIN_TTL = 0.001` 초 이상의 유한한 숫자 (정수 · 소수 모두, dev 와 같음). 1ms 보다 작으면 `지금 + ttl` 이 부동소수점에서 지금과 같아져 저장하자마자 만료된다.
- `0` · 음수 · `NaN` · `Infinity` · 불리언(`True`) · 문자열 → `ValueError`. 서버는 이것을 400으로 바꾼다.
- `10**400` 같은 너무 큰 정수는 `MIN_TTL <= ttl <= sys.float_info.max` 범위 비교로 `ValueError` 거부한다 (NaN · Infinity 도 이 비교 하나로 걸러진다).

**`ttl` 반환을 올림으로 하는 이유**: 남은 시간이 0.3초여도 키는 아직 살아 있다. 내림이면 살아 있는 키가 `0`을 돌려줘서 "곧 없어짐"과 구별이 안 된다.

## 4. 해시 테이블 결정 (다음 설계 1 · 2 · 3)

| 결정 | 선택 | 이유 |
|---|---|---|
| 처음 크기 | 8칸 (뼈대 기본값) | 작게 시작해 필요할 때만 늘린다 |
| 해시 함수 | **FNV-1a 64비트** 모듈 함수 `fnv1a` (dev 와 같음, 키를 UTF-8 바이트로 바꿔 계산) | 5줄로 짧고 분포가 고르다. 파이썬 내장 `hash()` 는 실행할 때마다 값이 바뀌어(`PYTHONHASHSEED`) 테스트 재현이 어렵다 |
| 충돌 처리 | **Separate Chaining** (칸마다 리스트) | 삭제가 "리스트에서 빼기"로 끝난다. 개방 주소법은 삭제 표시(tombstone)를 따로 관리해야 한다 |
| 리사이즈 | 부하율(`size / 칸 수`) **> 0.75** 이면 칸 **2배** | 칸 하나에 줄 선 항목이 평균 1개 아래로 유지 → 평균 O(1) |
| 줄이기 | 하지 않음 | 지운 뒤 다시 쓰는 경우가 많고, 코드만 늘어난다 |

```python
def fnv1a(key):
    if not isinstance(key, str):
        raise TypeError(...)
    h = 0xCBF29CE484222325                # FNV offset basis (64비트)
    for byte in key.encode("utf-8", "surrogatepass"):  # 짝 없는 반쪽 문자("\ud800")도 str 이라 받아야 한다
        h ^= byte
        h = (h * 0x100000001B3) & MASK_64 # FNV prime, 64비트로 자름
    return h
```

## 5. 데이터 흐름

### 5-1. 저장 `set(key, value, ttl)`
1. (서버) 요청 경로에서 key, 본문 JSON에서 value · ttl 추출 · 검사 → 틀리면 400
2. (store) 락을 잡는다
3. (hashtable) `_data` 에서 `_index(key)` 로 칸 번호 계산 → 같은 key 가 있으면 값만 바꾸고, 없으면 `[key, value]` 를 붙이고 `size += 1` → 부하율 > 0.75 이면 칸 2배 리사이즈
4. ttl 이 있으면 `_expires` 에 `clock() + ttl`, 없으면 `_expires` 에서 지운다 (SET 규칙)
9. 락을 놓고 성공 결과 반환 → (서버) 200 `{"ok": true}`

### 5-2. 조회 `get(key)` — 지연 삭제 포함
1. 락을 잡는다
2. `_data` 에 키가 없으면 `None`
3. `_expires` 의 만료 시각이 지났으면 **두 테이블에서 그 자리에서 지우고** `None` (지연 삭제)
4. 살아 있으면 `value` 반환 → (서버) 200, `None` 이면 404

### 5-3. 만료 처리 (다음 설계 5) — 두 방법을 함께 쓴다

| 방법 | 언제 | 없으면 생기는 문제 |
|---|---|---|
| **지연 삭제** | `get` · `get_with_ttl` · `exists` · `delete` · `expire` · `ttl` 이 키를 볼 때마다 | `sweep` 주기 사이에 만료된 값이 응답으로 나간다 |
| **주기 삭제** `sweep()` | 서버의 백그라운드 스레드가 **1초마다** | 아무도 다시 읽지 않는 만료 키가 메모리에 영원히 남는다 |

- `sweep` 은 `_expires.keys()` 로 만료가 있는 키만 훑는다 (O(만료 키 수)).
  `shortcut: 만료 키가 수십만 개면 1초마다 훑기가 느려진다 → 그때 실제 Redis처럼 무작위 20개 표본 검사로 바꾼다`

## 6. 캐시 무효화 (다음 설계 6)

- 저장소 쪽 무효화는 `delete(key)` 하나 (+ TTL 자동 만료). 따로 만들 기능은 없다.
- 정책은 `demo/api_server.py` 에서 쓴다 — **Cache-Aside + 버전 키** (dev 파일 그대로):
  1. 원본 아이템마다 `version` 이 있고, 캐시 키는 `item:{id}:v{version}`
  2. 읽기: 지금 버전의 키(`GET /keys/item:{id}:v{n}`) 확인 → 있으면 바로 응답 (hit)
  3. 없으면(miss) 느린 원본 `fetch_item` 조회 → "읽은 데이터의 버전 == 지금 버전" 일 때만 그 버전 키에 `ttl=60` 으로 저장 → 응답
  4. 원본을 바꾸면 버전을 올린다 → 그 순간 옛 키는 읽히지 않는다 (무효화 완료). 옛 키 `DELETE` 는 메모리 정리용
- **왜 버전 키인가**: "수정 후 삭제" 만 하면, 느린 읽기(200ms) 도중 수정 + 삭제가 끼었을 때 그 읽기가 옛 값을 늦게 저장해 최대 60초 옛 값이 보인다. 버전 키면 옛 데이터는 옛 키로만 가고(그나마 버전 확인으로 저장도 안 함), 새 요청은 새 키만 읽는다.
- `fetch_item` 은 실제 DB 처럼 "읽은 뒤 늦게 도착" 하도록 먼저 읽고 기다린다 → 위 경쟁 상태를 테스트로 실제로 만들 수 있다.
- TTL 60초는 옛 키 삭제를 놓쳤을 때의 메모리 안전망.
  `shortcut: 버전 확인(current_version)은 가벼운 조회라고 가정해 지연을 넣지 않았다. 실제 서비스면 버전을 캐시에 따로 둔다`
- Mini Redis 가 꺼져 있거나 1초 안에 답하지 않거나, 약속과 다른 응답(JSON 아님 · `value` 없음)을 주거나, 캐시 저장이 실패하면 원본만 읽어 응답한다 (`"cache": "BYPASS"`). 캐시는 빠르게 하려는 것이지 없으면 안 되는 것이 아니다.
- Mini Redis 호출은 `RedisClient` 클래스(`get` · `set` · `delete`)가 맡고, 실패는 모두 `RedisUnavailable` 하나로 통일한다.

## 7. 동시성 (다음 설계 7)

- 서버는 `http.server.ThreadingHTTPServer` → 요청마다 스레드가 따로 돈다. `sweep` 스레드도 동시에 돈다.
- `MiniRedis` 에 **`threading.Lock` 하나**. 모든 공개 메서드는 `with self._lock:` 안에서 실행한다.
- 락이 꼭 필요한 곳 (확인한 뒤 쓰는 동작 — 사이에 다른 스레드가 끼면 틀린다):
  - "만료 확인 → 삭제" (지연 삭제, `sweep`)
  - "같은 키 있음? → 갱신 / 없음 → 삽입" + `size` 증가 + 리사이즈
  - `expire`: "키 있음? → 만료 설정"
- `HashTable` 자체는 락이 없다. 혼자 쓰면 락이 필요 없고, 동시성은 위 계층 책임으로 둔다.
- 서버의 연결 대기열(`request_queue_size`)은 128. 표준 라이브러리 기본값 5 로는 클라이언트 수십 개가 동시에 접속할 때 넘친 연결이 끊긴다 (검증 중 발견).
- 락 하나라 요청이 한 줄로 처리되지만, 각 명령이 마이크로초 단위라 HTTP 처리 시간에 비해 무시할 수 있다.
  `shortcut: 락 하나가 병목이 되면(초당 수만 요청) 칸 범위별로 락을 나눈다`

## 8. HTTP API (다음 설계 8)

뼈대 `server.py` 주석의 경로를 그대로 쓴다. 요청 · 응답 본문은 모두 JSON (`Content-Type: application/json; charset=utf-8`).

| 메서드 · 경로 | 요청 본문 | 성공 | 실패 |
|---|---|---|---|
| `GET /keys/{key}` | — | 200 `{"key": k, "value": v, "ttl": n}` (값과 ttl 을 `get_with_ttl` 로 함께 읽음) | 404 `{"error": "키가 없습니다"}` |
| `PUT /keys/{key}` | `{"value": v, "ttl": 초(선택)}` | 200 `{"ok": true}` | 400 (본문 · ttl 오류) |
| `DELETE /keys/{key}` | — | 200 `{"deleted": true/false}` | — |
| `GET /keys/{key}/ttl` | — | 200 `{"ttl": n}` (-1 / -2 포함) | — |
| `POST /keys/{key}/expire` | `{"ttl": 초}` | 200 `{"ok": true}` | 404 키 없음 · 400 ttl 없음 · 오류 |
| `GET /health` | — | 200 `{"keys": 저장된 키 수}` | 405 (GET 이 아님) |
| 그 밖의 경로 · 빈 키(`/keys/`) | — | — | 404 `{"error": "없는 경로입니다"}` |
| 경로는 맞고 메서드가 다름 (`PATCH` · `OPTIONS` 포함) | — | — | 405 — `/keys/{key}` 는 `"GET / PUT / DELETE만 지원합니다"`, `/ttl` · `/health` 는 `"GET만 지원합니다"`, `/expire` 는 `"POST만 지원합니다"` |

**입력 검사 (신뢰 경계 — 서버에서 반드시)**
- key: URL 디코딩(`urllib.parse.unquote`), 빈 문자열이면 404 (없는 경로, dev 와 같음).
- 본문: JSON 객체가 아니면 400. `value` 키가 없으면 400 (`null` 은 값으로 허용하지 않는다 — `get` 의 `None` 과 구별이 안 되므로).
- 본문 크기: `Content-Length` 가 1MB 를 넘으면 413. 없거나 숫자가 아니면 400.
  - 413 을 보내기 전에 본문을 읽어서 버린다(최대 16MB). 읽지 않고 연결을 닫으면 운영체제가 강제 끊김(RST)을 보내, 본문을 보내던 클라이언트는 413 을 받기 전에 `Connection reset` 을 본다.
  `shortcut: 16MB 보다 큰 본문은 다 버리지 못하고 끊긴다 → 그런 클라이언트가 실제로 있으면 응답 후 소켓 shutdown 방식으로 바꾼다`
- 본문 JSON 에 `NaN` · `Infinity` 가 있거나, 너무 깊게 중첩되거나, 짝 없는 반쪽 문자(`"\ud800"`)가 있으면 400. 둘 다 응답으로 다시 쓸 수 없는 값이라(`RecursionError` · `UnicodeEncodeError`) 저장 전에 UTF-8 JSON 으로 한 번 써 보고 거부한다 (dev 와 같음).
- 본문을 10초(`REQUEST_TIMEOUT`) 안에 다 받지 못하면 408 (보내다 멈춘 클라이언트가 스레드를 붙잡지 못하게). 제한 시간은 연결마다 모듈 값을 다시 읽는다 (테스트가 값을 바꿀 수 있게).
- ttl: 3장 규칙. 위반이면 400.
- 응답은 한글을 글자 그대로 보낸다. 파이썬 코드로 저장소에 직접 넣은 반쪽 문자처럼 UTF-8 로 못 바꾸는 값만 `\uXXXX` 로 적어 응답이 반드시 나가게 한다.
- 서버 안에서 예상 못 한 예외 → 500 `{"error": "서버 내부 오류"}` (스레드가 죽지 않게).

**오류 문구** — 모두 `{"error": "이유"}` 이고 문구는 dev 와 같은 한국어다.

| 상태 | 상황 | 문구 |
|---|---|---|
| 400 | Content-Length 없음 · 숫자 아님 | `Content-Length가 올바르지 않습니다` |
| 400 | JSON 아님 · `NaN` · `Infinity` · UTF-8 아님 | `본문이 올바른 JSON이 아닙니다 (NaN / Infinity 불가)` |
| 400 | 너무 깊은 중첩 | `JSON이 너무 깊게 중첩되어 있습니다` |
| 400 | 객체가 아닌 본문 | `본문은 JSON 객체({...})여야 합니다` |
| 400 | 짝 없는 반쪽 문자 | `UTF-8로 표현할 수 없는 문자(짝 없는 서로게이트)가 들어 있습니다` |
| 400 | `value` 없음 · `null` | `value가 필요합니다 (null은 저장할 수 없습니다)` |
| 400 | expire 에 `ttl` 없음 | `ttl이 필요합니다` |
| 400 | 잘못된 ttl (`store.py` 의 `ValueError` 그대로) | `ttl은 0.001초 이상의 유한한 숫자여야 합니다` |
| 404 | 키 없음 · 만료됨 | `키가 없습니다` |
| 404 | 없는 경로 · 빈 키 | `없는 경로입니다` |
| 408 | 제한 시간 안에 본문을 못 받음 | `요청 본문을 제한 시간 안에 다 받지 못했습니다` |
| 413 | 1MB 초과 | `요청 본문이 너무 큽니다 (최대 1MB)` |
| 500 | 예상 못 한 오류 | `서버 내부 오류` |

**실행**: `projects/redis` 에서 `python -m mini_redis.server --port 6380` (기본 `127.0.0.1` — 외부에 열지 않는다).

## 9. 영속성 (다음 설계 9 · 선택)

RDB 방식(스냅샷)을 참고한다. AOF(명령 기록)는 하지 않는다. **김건희 님 브랜치(`feat/Kimgeonhui-Redis`)의 구현을 그대로 써서 파일 형식 · 동작을 팀과 맞췄다** (dev 에는 아직 TODO).

| 함수 | 동작 |
|---|---|
| `MiniRedis.dump()` | 락 하나 안에서 만료되지 않은 모든 키 → `[(키, 값, 남은 초 또는 None)]` ("한 시점의 사진") |
| `save_snapshot(store, path)` | `dump()` 결과를 JSON 파일로 저장 → 저장한 키 수 |
| `load_snapshot(store, path)` | 파일을 읽어 **모든 항목을 먼저 검사**한 뒤 `store.set(key, value, ttl)` 로 복구 → 복구한 키 수. 파일이 없으면 0 (처음 켜는 서버) |
| `start_periodic_snapshot(store, path, interval)` | `interval` 초마다 저장하는 스레드 시작 → `stop()` 함수를 돌려줌 (멈출 때 마지막으로 한 번 더 저장) |

**파일 모양** (`data/dump.json`):

```json
{"format": 1, "saved_at": 1794490976.3, "entries": [{"key": "user:1", "value": {"name": "철수"}, "ttl": null},
                                                    {"key": "session", "value": "s", "ttl": 27.4}]}
```

- **남은 시간 + 저장 시각**: `monotonic` 값은 재시작하면 의미가 없으므로 "남은 초" 를 적고, 저장한 벽시계 시각(`saved_at`, `time.time()`)도 적는다. 복구할 때 **꺼져 있던 시간(지금 − saved_at)만큼 빼서** 다시 건다. 0.001초 미만이 되면 꺼져 있는 동안 만료된 것이라 복구하지 않는다.
- **원자적 저장**: `path + ".tmp"` 에 끝까지 쓰고 `fsync` 로 디스크에 내린 뒤 `os.replace` 로 바꾼다 → 쓰는 도중 꺼져도 이전 스냅샷이 온전히 남는다. 실패하면 임시 파일만 지운다. (Windows 에서 다른 프로그램이 파일을 열고 있으면 잠깐 기다렸다 다시 시도)
- **반쪽 문자도 저장**: `ensure_ascii` 기본값으로 써서 `"\ud800"` 같은 값도 파일에 쓰고 그대로 읽어 온다.
- **손상된 파일**: 형식 · `saved_at` · 키 · ttl 이 이상하면 `SnapshotError`. 서버는 **시작하지 않는다** — 빈 서버로 떴다가 다음 저장 때 그 파일을 덮어써 데이터가 영영 사라지는 것을 막는다. 검사는 저장소에 넣기 **전에** 모두 끝내서, 일부만 복구되는 일이 없다.
- **저장 시점**: 60초마다(`--snapshot-interval`) + 서버를 끌 때(Ctrl+C). 저장 실패는 서버를 멈추지 않고 다음 주기에 다시 시도한다.
- **서버 옵션**: `python -m mini_redis.server --snapshot data/dump.json --snapshot-interval 60` (기본값). `--snapshot ""` 이면 저장 · 복구를 하지 않는다. 파일 위치 `projects/redis/data/` 는 `.gitignore` 에 있다.
- **한계**: 마지막 저장 뒤 바뀐 데이터는 서버가 갑자기 죽으면(전원 · `kill -9`) 잃는다 (최대 60초치). 캐시 용도라 원본에서 다시 가져오면 되므로 받아들인다. 테스트 GUI(`tests.gui`) · 벤치마크는 `create_server` 만 써서 스냅샷을 쓰지 않는다.

## 11. 데모 · 성능 비교

- `demo/api_server.py` (dev 파일 그대로): `fetch_item` 은 원본을 읽은 뒤 `time.sleep(0.2)` 로 느린 DB 를 흉내. 아이템 1~100.
  - `GET /items/{id}` (캐시 사용) → `{"item": {...}, "cache": "HIT" | "MISS" | "BYPASS"}` · 없는 아이템 404
  - `GET /items/{id}?cache=off` (매번 원본) → `"cache": "OFF"`
  - `PUT /items/{id}` body `{"price": 유한한 숫자}` → 원본 수정 + 버전 올림(무효화) + 옛 버전 키 삭제 → `{"item": {...}, "old_cache_deleted": bool}`
  - 서버 생성: `create_demo_server(redis_url, host, port)`
- `demo/benchmark.py`: 같은 id 를 n=20 번 요청해 평균 응답 시간(ms) 을 표로 출력.
  - `python -m demo.benchmark` 만 치면 Mini Redis · 데모 API 서버를 프로그램 안에서 빈 포트로 띄워 잰다. 이미 띄운 서버는 `--api` 로 지정.
  - 측정 (2026-11-12, n=20, 검증 때): 캐시 미사용 **204.58ms**, 캐시 사용 **11.32ms** (첫 요청 MISS 포함) → 약 **18.1배**.

## 13. 하지 않는 것

- Redis 의 다른 자료형(List · Set · Hash · Sorted Set), RESP 프로토콜, 복제 · 클러스터, 메모리 한도 · LRU 제거.
