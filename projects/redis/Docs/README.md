# Mini Redis

해시 테이블을 직접 만들어(파이썬 `dict` 사용 X) 그 위에 **키-값 저장 · 만료(TTL) · 동시성 제어 · HTTP JSON API · 스냅샷 영속성** 을 올린 작은 Redis 입니다.
느린 API 앞에 캐시로 붙여 성능이 얼마나 좋아지는지도 보여 줍니다.

- 언어: Python 3.10 이상, **표준 라이브러리만** (설치할 것 없음) · Python 3.14.7 · macOS (Apple M5) 에서 검증
- 브랜치: `feat/Kimjunwoo-Redis` (김준우)
- 테스트: 제 테스트 **95개** + 팀원(dev) 테스트 **61개** 모두 통과 · 브라우저 **테스트 GUI** 있음 (13장)
- 성능: 같은 요청 20번 평균 **204.58ms → 11.32ms (약 18배)** · HTTP 처리량 약 **5,000 요청/초**, 연결을 재사용하면 약 **9,000 ~ 12,700 요청/초** (8장)

## 3. HashTable 원리

### 3-1. 왜 해시 테이블인가

키로 값을 찾을 때 리스트를 처음부터 훑으면 키가 n 개일 때 최악 n 번 비교합니다 (O(n)). 해시 테이블은 **키를 숫자로 바꿔 그 숫자 번째 칸으로 바로 갑니다.** 칸 안에 항목이 한두 개뿐이면 비교도 한두 번이라 평균 O(1) 입니다.
과제 규칙상 파이썬 `dict`(그 자체가 해시 테이블)는 쓸 수 없어서 직접 만들었습니다.

```
키 ──fnv1a──▶ 64비트 정수 ──% 칸 수──▶ 칸 번호 ──▶ 그 칸의 리스트를 앞에서부터 보며 키 비교
```

### 3-2. 생김새 — 칸(bucket)마다 리스트

```python
self._buckets = [[] for _ in range(capacity)]   # 처음 8칸
self._size = 0                                  # 저장된 항목 수
```

`k0` ~ `k5` 6개를 넣은 실제 모습 (8칸):

```
[0] [ ["k2", 2] ]      [4] [ ]
[1] [ ["k1", 1] ]      [5] [ ["k5", 5] ]
[2] [ ["k4", 4] ]      [6] [ ["k0", 0] ]
[3] [ ["k3", 3] ]      [7] [ ]
```

- 칸 하나 = 파이썬 리스트, 항목 하나 = `[key, value]` **리스트** (튜플이면 값을 바꿀 때 새로 만들어야 함 — 리스트라 `entry[1] = value` 한 줄).
- `[[]] * n` 이 아니라 `[[] for _ in range(n)]`: 앞의 것은 **같은 리스트 하나를 n 번 가리켜** 한 칸에 넣으면 모든 칸에 들어간 것처럼 됩니다.
- `_size` 를 따로 세서 `len()` 이 O(1) 입니다 (매번 칸을 다 세면 O(n)).

### 3-3. 해시 함수 — FNV-1a 64비트

```python
FNV_OFFSET = 0xCBF29CE484222325   # 시작 값 (표준)
FNV_PRIME  = 0x100000001B3        # 곱하는 소수 (표준)
MASK_64    = (1 << 64) - 1

def fnv1a(key):
    h = FNV_OFFSET
    for byte in key.encode("utf-8", "surrogatepass"):
        h ^= byte                         # 1) 바이트 하나를 섞고 (XOR)
        h = (h * FNV_PRIME) & MASK_64     # 2) 소수를 곱해 퍼뜨린 뒤 64비트로 자른다
    return h
```

실제 계산 — `fnv1a("ab")`:

| 단계 | 바이트 | XOR 결과 | × 소수 후 64비트로 자름 |
|---|---|---|---|
| 시작 | — | — | `0xcbf29ce484222325` |
| 1 | `0x61` (`a`) | `0xcbf29ce484222344` | `0xaf63dc4c8601ec8c` |
| 2 | `0x62` (`b`) | `0xaf63dc4c8601ecee` | `0x089c4407b545986a` |

- **XOR 다음 곱하기**: 글자 하나만 달라도 결과 전체가 크게 바뀌어(눈사태 효과) 키들이 칸에 고르게 퍼집니다. (XOR 이 먼저면 FNV-1a, 곱하기가 먼저면 FNV-1)
- **`& MASK_64`**: 파이썬 정수는 끝없이 커지므로 C 의 64비트 정수처럼 넘친 부분을 잘라 냅니다.
- **UTF-8 바이트로**: 한글 `메이플` 도 9바이트로 바뀌어 같은 방식으로 계산됩니다 (`0xfcd5f29a0311e98f`).
- **`surrogatepass`**: 짝 없는 반쪽 문자(`"\ud800"`)도 파이썬 `str` 이라 받아야 하는데, 그냥 UTF-8 로 바꾸면 오류가 납니다.
- 키가 문자열이 아니면 `TypeError` — 숫자 키는 위 계층의 실수라 바로 알립니다.

### 3-4. 칸 번호와 충돌 — 체이닝

칸 번호 = `fnv1a(key) % 칸 수`.

| 키 | `fnv1a(key)` | 8칸일 때 | 16칸일 때 |
|---|---|---|---|
| `user:1` | `0xf7fd9aaa75081ceb` | 3 | 11 |
| `name` | `0xc4bcadba8e631b86` | 6 | 6 |
| `메이플` | `0xfcd5f29a0311e98f` | 7 | 15 |
| `hi` | `0x08ba5f07b55ec3da` | **2** | **10** |
| `post:9` | `0x004585d7b76370ba` | **2** | **10** |

`hi` 와 `post:9` 는 다른 키인데 같은 칸입니다 — **충돌**. 칸은 유한하고 키는 무한하니 충돌은 반드시 생깁니다. 체이닝은 **같은 칸의 리스트에 하나 더 붙입니다**:

```
[2] [ ["hi", …], ["post:9", …] ]
```

찾을 때는 그 칸 리스트를 앞에서부터 보며 **키 문자열이 정확히 같은** 항목을 찾습니다 (`entry[0] == key`). 해시가 같아도 섞이지 않습니다.

| 동작 | 칸 안에서 하는 일 |
|---|---|
| `set` | 같은 키가 있으면 `entry[1] = value` (항목 수 그대로), 없으면 `append([key, value])` 후 `_size += 1` → 리사이즈 검사 |
| `get` · `in` | 같은 키를 찾아 `entry[1]` / 있음 여부 (`None` 값도 "있음") |
| `delete` | 같은 키를 찾아 `del bucket[i]` 후 `_size -= 1` — 개방 주소법처럼 "삭제됨" 표시를 남길 필요가 없음 |

### 3-5. 부하율과 리사이즈

**부하율** = 항목 수 ÷ 칸 수. 높으면 한 칸에 여러 개가 줄 서서 찾기가 느려집니다. 새 키를 넣은 뒤 **부하율 > 0.75 이면 칸을 2배로** 늘리고 모든 항목을 다시 넣습니다.

| 넣은 키 | 항목 수 | 칸 수 | 부하율 | |
|---|---|---|---|---|
| `k0` ~ `k5` | 1 → 6 | 8 | 0.125 → **0.750** | 0.75 는 "넘지" 않았으므로 그대로 |
| `k6` | 7 | 8 → **16** | 0.875 → 0.438 | 넘는 순간 2배 |

리사이즈 뒤 16칸: `[1] k1  [4] k6  [8] k2  [10] k4  [11] k3  [13] k5  [14] k0` — 칸 수가 바뀌면 같은 키도 칸 번호가 바뀌므로(`k2` 0 → 8) **모두 다시 계산해서 옮겨야** 합니다.

```python
def _resize(self, new_capacity):
    new_buckets = [[] for _ in range(new_capacity)]
    for bucket in self._buckets:
        for entry in bucket:
            new_buckets[fnv1a(entry[0]) % new_capacity].append(entry)   # 항목 리스트는 새로 만들지 않고 옮김
    self._buckets = new_buckets
```

- 리사이즈 한 번은 O(n) 이지만 칸이 2배씩 늘어서 드뭅니다. 키 10만 개를 넣는 동안 리사이즈는 **15번**뿐입니다 (8 → 262,144칸). 옮기는 총량이 1 + 2 + 4 + … ≈ 2n 이라 **저장 한 번당 평균 O(1)** 입니다 (분할 상환).
- 줄이지는 않습니다 (7장).

### 3-6. 실제로 고르게 퍼지나 — 분포 측정

`user:0` ~ `user:99999` 10만 개를 넣고 칸마다 줄 길이를 세어 봤습니다 (측정 방법 8-2).

| 항목 | 값 |
|---|---|
| 칸 수 · 부하율 | 262,144칸 · 0.381 |
| 빈 칸 | **69.9%** (완전히 무작위인 해시의 이론값 68.3% 와 거의 같음) |
| 가장 긴 줄 | **5** |
| 키가 있는 칸의 평균 줄 길이 | **1.27** |
| 줄 길이별 칸 수 | 0개: 183,140 · 1개: 61,334 · 2개: 14,708 · 3개: 2,616 · 4개: 328 · 5개: 18 |

`user:0`, `user:1` … 처럼 끝 한두 글자만 다른 키들도 무작위에 가깝게 퍼집니다. 그래서 찾기 한 번에 비교가 평균 1~2번입니다.

## 5. 내부 동작 흐름

### 5-1. 저장 — `PUT /keys/user:1` body `{"value": "Nameisme", "ttl": 60}`

```
운영체제 대기열(128칸) ─▶ ThreadingHTTPServer 가 연결마다 스레드 하나 생성 ─▶ Handler.setup (읽기 제한 10초 · TCP_NODELAY)
  ─▶ (HTTP/1.1) 클라이언트가 연결을 닫지 않으면 아래를 같은 연결 · 같은 스레드에서 요청마다 되풀이
  ─▶ do_PUT ─▶ _handle ─▶ _route
        경로 "/keys/user:1" ─split("/")─▶ ["keys", "user:1"] ─조각마다 unquote─▶ 키 "user:1"
  ─▶ _read_json
        Content-Length 숫자? ─▶ 1MB 이하? ─▶ 10초 안에 다 받음? ─▶ JSON? (NaN 거부) ─▶ 객체? ─▶ 다시 쓸 수 있나?
  ─▶ value 있고 null 아님?
  ─▶ _call(store.set, "user:1", "Nameisme", 60)
        _check_ttl(60)                      ← 락 밖. 틀리면 ValueError → 400, 아무것도 안 바뀜
        with lock:
            _data.set("user:1", "Nameisme")  ─▶ fnv1a → % 8 = 3번 칸 → 같은 키 없음 → append → _size 1 → 1/8 ≤ 0.75
            _expires.set("user:1", 지금 + 60)
  ─▶ _send(200, {"ok": true})
```

### 5-2. 조회 — `GET /keys/user:1` (지연 삭제 포함)

```
_route ─▶ store.get_with_ttl("user:1")
            with lock:
                _alive: "user:1" in _data?          아니면 → (None, -2) → 404 "키가 없습니다"
                        만료 시각 <= 지금?           그렇면 → 두 테이블에서 지우고 (None, -2) → 404
                값 = _data.get, ttl = ceil(만료 시각 − 지금) 또는 -1
         ─▶ 200 {"key": "user:1", "value": "Nameisme", "ttl": 60}
```

### 5-3. 만료되는 두 길

```
시간 ─────────────────────────────────────────────────────────────────▶
 t=0      PUT short ttl 0.5
 t=0.5    (만료 시각. 아직 메모리에 있음)
 t=0.7    GET short ─▶ _alive 가 보고 그 자리에서 지움 ─▶ 404          ← 지연 삭제
 ...
 t=0      PUT other ttl 0.2   (아무도 다시 안 읽음)
 t≤1.2    정리 스레드의 sweep() ─▶ _expires 를 훑다가 지움            ← 주기 삭제 (1초마다)
```

어떤 길로 오든 만료된 값은 응답으로 나가지 않고, 메모리에도 최대 약 1초만 남습니다.

### 5-4. 잘못된 요청은 어디서 걸리나

| 순서 | 검사 | 걸리면 |
|---|---|---|
| 1 | 경로 모양 (`/keys/{key}`, `/keys/{key}/ttl`, `/keys/{key}/expire`, `/health`) · 빈 키 | 404 `없는 경로입니다` |
| 2 | 그 경로가 받는 메서드인가 | 405 (경로마다 받는 메서드를 알려 줌) |
| 3 | `Content-Length` 가 ASCII 숫자인가 | 400 |
| 4 | 1MB 이하인가 | 본문을 읽어 버린 뒤 413 |
| 5 | 10초 안에 본문을 다 받았나 | 408 |
| 6 | JSON 인가 (`NaN` · `Infinity` 거부) | 400 |
| 7 | 객체 `{...}` 인가 | 400 |
| 8 | 응답으로 다시 쓸 수 있나 (너무 깊은 중첩 · 반쪽 문자) | 400 |
| 9 | `value` 있고 `null` 아님 / `ttl` 있음 | 400 |
| 10 | ttl 규칙 (저장소 `_check_ttl`) | 400 |
| — | 그 밖의 예상 못 한 예외 | 500 (서버는 계속) |

### 5-5. 서버가 켜지고 꺼지기까지

```
python -m mini_redis.server
  1. 인자 확인 (--snapshot-interval 은 0보다 큰 유한한 수)
  2. MiniRedis() 생성
  3. load_snapshot("data/dump.json")      파일 없음 → 0개 / 손상 → SnapshotError → 시작 거부 (종료 코드 1)
  4. create_server()                      포트를 못 열면 친절한 오류로 종료
       └─ 정리 스레드 시작 (1초마다 sweep)
  5. start_periodic_snapshot()            저장 스레드 시작 (60초마다 save)
  6. serve_forever()                      연결마다 스레드 (한 연결로 요청 여러 개, 10초 쉬면 닫음)
  ── Ctrl+C ──
  7. server_close()                       정리 스레드 멈춤 · 소켓 닫기
  8. stop_snapshot()                      저장 스레드 멈춤 → 마지막으로 한 번 더 저장
```

### 5-6. 스냅샷 저장 · 복구

```
저장   store.dump()  (락 안: 만료 안 된 키 → (키, 값, 남은 초))
         ─▶ {"format": 1, "saved_at": time.time(), "entries": [...]}
         ─▶ dump.json.tmp 에 쓰기 ─▶ fsync ─▶ os.replace(tmp → dump.json)

복구   dump.json 읽기 ─▶ format · saved_at · 모든 항목의 키 · ttl 먼저 검사 (하나라도 이상하면 SnapshotError, 아무것도 안 넣음)
         ─▶ 꺼져 있던 시간 = time.time() − saved_at
         ─▶ 항목마다 ttl − 꺼져 있던 시간 < 0.001 이면 건너뜀, 아니면 store.set(key, value, ttl)
```

실측: ttl 30 짜리 키를 저장하고 서버를 3초 꺼 두었다가 켜면 ttl **27** 로 복구됩니다.

### 5-7. 캐시 데모 — `GET /items/1` 과 `PUT /items/1`

```
GET  current_version(1) = v1
       ─▶ Mini Redis GET item:1:v1 ── 있음 ─▶ HIT (수 ms)
                                    └ 없음 ─▶ fetch_item (원본 읽고 0.2초) ─▶ 읽은 버전 == 지금 버전? ─▶ PUT item:1:v1 ttl 60 ─▶ MISS
       (Mini Redis 실패 · 이상한 응답 ─▶ 원본만 읽고 BYPASS)
PUT  원본 수정 + 버전 v1 → v2   (이 순간부터 item:1:v1 은 아무도 안 읽음 = 무효화 완료)
       ─▶ Mini Redis DELETE item:1:v1 (메모리 정리) ─▶ {"item": …, "old_cache_deleted": true}
```

| 영속성 | 종료 때 한 번, 꺼진 시간 미반영 | 60초마다 + 종료 때, 꺼진 시간 반영 | 김건희 님 브랜치와 맞춤 |

## 7. 설계 이유

### 7-1. 해시 테이블

| 결정 | 고른 것 | 버린 것 | 이유 |
|---|---|---|---|
| 해시 함수 | **FNV-1a 64비트** | 파이썬 `hash()` | `hash()` 는 문자열 값이 실행마다 바뀌어(`PYTHONHASHSEED`) "어느 키가 몇 번 칸" 을 테스트에서 재현할 수 없다. FNV-1a 는 짧고 항상 같은 값이며, 실제 분포가 무작위 해시와 거의 같다 (3-6) |
| 충돌 처리 | **체이닝** | 개방 주소법 | 개방 주소법은 중간 항목을 지우면 뒤 항목을 못 찾게 되어 "삭제됨" 표시(tombstone)를 관리해야 한다. 체이닝은 리스트에서 빼면 끝 |
| 리사이즈 | 부하율 **0.75 초과 → 2배** | 더 높은 기준 · 조금씩 늘리기 | 0.75 이하면 칸당 평균 1개 미만. 2배씩이면 리사이즈가 드물어 평균 O(1) (10만 개에 15번) |
| 줄이기 | **안 함** | 비면 절반으로 | 캐시는 지운 뒤 다시 채우는 일이 많아 줄였다 늘였다 반복하게 되고, 경계 코드만 는다 |
| `keys()` | **새 리스트** | 내부 리스트 그대로 | `sweep()` 이 돌면서 지워도 키를 빠뜨리지 않는다 |

### 7-2. 저장소

| 결정 | 고른 것 | 버린 것 | 이유 |
|---|---|---|---|
| 저장 구조 | 테이블 **2개** (값 · 만료 시각) | 1개 | 실제 Redis 와 같은 구조. 만료 있는 키만 `_expires` 에 있어 정리 비용이 만료 키 수에만 비례 |
| 만료 처리 | **지연 + 주기 둘 다** | 하나만 | 지연만: 안 읽는 만료 키가 메모리에 영원히 남음. 주기만: 정리 사이(최대 1초) 만료 값이 응답으로 나감 |
| 만료 경계 | 같은 순간도 만료 (`<=`) | `<` | ttl=1 로 저장하고 정확히 1초 뒤에는 없어야 한다 |
| 시계 | **`monotonic`** + `clock` 매개변수 | `time.time()` | 벽시계는 NTP 보정 · 수동 변경으로 뒤로 갈 수 있다. 테스트는 가짜 시계로 60초를 0초에 흘린다 |
| 남은 시간 | **올림** | 내림 | 0.3초 남은 키가 `0` 이면 "없음" 과 헷갈린다 |
| ttl 최솟값 | **0.001초** | 제한 없음 | `1000.0 + 1e-14 == 1000.0` — 아주 작은 ttl 은 저장하자마자 만료된다. Redis `PEXPIRE` 도 1ms 단위 |
| ttl 검사 | 락 **밖에서 먼저** | 락 안 | 틀리면 아무것도 바꾸지 않고 바로 실패. 락도 안 잡는다 |
| 값 + ttl | **`get_with_ttl`** 한 번에 | `get()` 후 `ttl()` | 사이에 `delete` 가 끼면 `{"value": "값", "ttl": -2}` 같은 모순이 나온다 |

### 7-3. 서버

| 결정 | 이유 |
|---|---|
| 경로를 **나눈 뒤** 디코딩 | 키 `메이플/a` 의 `%2F` 를 먼저 풀면 키가 둘로 쪼개진다 |
| 저장 전에 응답으로 **한 번 써 보기** | 깊은 중첩 · 반쪽 문자가 "저장 성공, 조회 실패" 가 되지 않게 |
| `NaN` · `Infinity` · `null` 거부 | 표준 JSON 이 아님 / "없음" 과 구별 불가 |
| ttl 규칙은 저장소 한 곳에만 | 두 곳에 두면 언젠가 달라진다. 서버는 `ValueError` → 400 만 |
| 413 전 본문 버리기 · 408 · 대기열 128 | 각각 강제 끊김 · 스레드 붙잡힘 · 동시 접속 끊김을 막으려고 (9장) |
| HTTP/1.1 연결 재사용 (keep-alive) | 프로파일하면 요청 한 번(약 170µs)에서 저장소 명령은 약 2µs 뿐이고, 대부분이 TCP 연결 · 스레드를 새로 만드는 비용이었다. 해시 함수를 빠르게 해도 1% 밖이라, 이 비용을 없애는 쪽을 골랐다 (8-3) |
| 본문을 안 읽고 답하면 연결 닫기 | 연결을 재사용하면 읽지 않은 본문(예: 405 를 받은 `POST` 의 본문)이 같은 연결의 "다음 요청" 으로 읽혀 엉뚱한 응답이 나간다. 그런 응답에는 `Connection: close` 를 붙이고 닫는다 |
| `TCP_NODELAY` | 응답을 헤더 · 본문 두 번에 나눠 쓰는데, Nagle 알고리즘 + 상대의 지연 ACK 가 겹치면 연결 재사용 시 요청마다 최대 40ms 멈출 수 있다 (Linux). 실제 Redis 도 켠다 |
| 모든 응답 JSON (`PATCH` · `OPTIONS` 도 405 JSON) | 표준 라이브러리 기본은 HTML 501 |
| 기본 `127.0.0.1` | 인증이 없는 저장소라 외부에 안 여는 것이 기본 |

### 7-4. 스냅샷

| 결정 | 고른 것 | 버린 것 | 이유 |
|---|---|---|---|
| 방식 | **스냅샷** (RDB) | AOF | 파일이 작고 복구가 빠르다. 최대 60초치 손실은 캐시라 원본에서 다시 가져오면 된다 |
| 시간 | **남은 초 + 벽시계 저장 시각** | `monotonic` 만료 시각 | `monotonic` 은 재시작하면 0 부터. 꺼져 있던 시간을 빼야 ttl 이 정확하다 |
| 쓰기 | **`.tmp` → `fsync` → `os.replace`** | 바로 덮어쓰기 | 저장 도중 꺼져도 반쯤 쓰인 파일이 없다 |
| 복구 | **먼저 전부 검사** | 읽으면서 넣기 | 일부만 복구된 상태가 없게 |
| 손상 파일 | **시작 거부** | 빈 서버로 시작 | 빈 서버로 뜨면 60초 뒤 그 파일을 덮어써 영영 잃는다 |

### 7-5. 캐시 데모

| 결정 | 이유 |
|---|---|
| **버전 키** (`item:{id}:v{n}`) + 저장 전 버전 확인 | "수정 후 삭제" 만 하면 느린 읽기가 옛 값을 늦게 저장해 60초 동안 옛 값이 나간다 (12장 그림) |
| Mini Redis 실패 시 **BYPASS** | 캐시는 빠르게 하려는 것. 캐시 장애가 서비스 장애가 되면 안 된다 |
| 데모는 Mini Redis 를 **HTTP 로만** 사용 | 진짜 Redis 를 쓰는 서비스와 같은 모양 |

## 8. 성능 측정 방법

모든 측정은 같은 컴퓨터 안(`127.0.0.1`)에서 했습니다. **환경**: Apple M5 (10코어) · macOS · Python 3.14.7. 숫자는 실행할 때마다 조금씩 달라집니다.

### 8-1. 캐시 효과 — `python -m demo.benchmark`

**무엇을**: 같은 아이템을 20번 요청할 때, 캐시를 쓰면 평균 응답 시간이 얼마나 줄어드는가.

**어떻게**

```python
def measure(url, n):
    total = 0.0
    for _ in range(n):
        start = time.perf_counter()          # 짧은 시간을 재는 가장 정밀한 시계
        with urlopen(url, timeout=10) as res:
            res.read()                        # 본문까지 다 받은 시간 (헤더만 받고 끝내면 덜 일한 것처럼 보임)
        total += time.perf_counter() - start
    return total / n * 1000                   # 평균 ms
```

1. Mini Redis 서버와 데모 API 서버를 **프로그램 안에서 빈 포트로** 띄웁니다 (새 저장소라 캐시가 비어 있음).
2. `GET /items/1?cache=off` 를 20번 — 매번 원본(0.2초).
3. `GET /items/1` 을 20번 — 첫 번째는 MISS(원본 + 저장), 나머지 19번은 HIT.
4. 평균을 표로 출력합니다.

**결과**

| 방식 | 평균 응답 시간 |
|---|---|
| 캐시 미사용 | 204.58ms |
| 캐시 사용 (첫 요청 MISS 포함) | 11.32ms |
| 차이 | 약 **18배** (여러 번 재면 17.7 ~ 18.6배) |

**해석**
- 캐시 미사용 ≈ 원본 지연 200ms + HTTP 왕복 약 5ms.
- 캐시 사용 평균은 MISS 1번(약 205ms)과 HIT 19번이 섞인 값입니다. (205 + 19 × h) / 20 = 11.32 를 풀면 **HIT 한 번은 약 1ms** — 데모 API → Mini Redis 로 HTTP 를 두 번 거치는 시간입니다.
- 요청 횟수가 많을수록 첫 MISS 의 비중이 줄어 차이가 더 커집니다 (`--n 100` 이면 MISS 가 1/100).

**재현**

```bash
python -m demo.benchmark --n 20 --id 1
```

이미 띄운 데모 서버로 재려면 `--api http://127.0.0.1:8000` (이때는 캐시가 이미 차 있을 수 있음).

### 8-2. 자료구조 연산 속도

**무엇을**: 직접 만든 해시 테이블과 저장소가 한 번에 얼마나 걸리는지, 파이썬 `dict` 와 비교해서.

**어떻게**: 키 `user:0` ~ `user:199999` 20만 개로 같은 연산을 20만 번 하고 `time.perf_counter()` 로 전체 시간을 잽니다. **세 번 재서 가장 빠른 값**을 씁니다 (다른 프로그램 · 가비지 컬렉션 때문에 느려진 회차를 빼려고). 측정 스크립트는 저장소에 넣지 않았습니다.

| 연산 | 1회 시간 | 초당 |
|---|---|---|
| `fnv1a` 해시 계산 | 551 ns | 182만 |
| `HashTable.get` | 799 ns | 125만 |
| `HashTable.set` (빈 표에서 20만 개, 리사이즈 포함) | 3,210 ns | 31만 |
| `MiniRedis.get` (락 + 만료 확인 + 테이블 2개) | 2,173 ns | 46만 |
| `MiniRedis.set` ttl 60 (락 + 테이블 2개) | 1,847 ns | 54만 |
| 파이썬 `dict` 조회 (비교) | 17 ns | 5,828만 |
| 파이썬 `dict` 저장 (비교) | 32 ns | 3,130만 |

**해석**
- 직접 만든 해시 테이블은 `dict` 보다 약 **47배 느립니다**. `dict` 는 C 로 짜여 있고, 우리 것은 파이썬 반복문으로 바이트마다 해시를 계산합니다. **조회 시간의 약 69% 가 `fnv1a` 계산**입니다 (파이썬 내장 `hash()` 는 C 로 계산하고 문자열에 결과를 캐시까지 함).
- 그래도 저장소 명령 한 번은 **약 2µs** 입니다. 아래 8-3 의 HTTP 요청 한 번(약 180µs)의 1% 정도라, 실제 서버에서는 자료구조가 병목이 아닙니다.

### 8-3. HTTP 처리량

**무엇을**: Mini Redis 서버가 초당 몇 개의 요청을 처리하는지, 클라이언트가 늘면 어떻게 되는지.

**어떻게**: 서버를 빈 포트에 띄우고, 스레드 1 · 4 · 20개가 `http.client` 로 `PUT` 을 보냅니다. 두 방식으로 잽니다.
- **새 연결**: 요청마다 연결을 새로 열고 `Connection: close` (urlopen 과 같은 방식)
- **연결 재사용**: 스레드마다 연결 하나를 열어 계속 씀 (HTTP/1.1 keep-alive — `requests.Session` · 브라우저 `fetch` 와 같은 방식)

세 번 재서 가장 빠른 값입니다.

| 동시 클라이언트 | 요청 수 | 새 연결 | 연결 재사용 | 배 | 오류 |
|---|---|---|---|---|---|
| 1 | 1,000 | 0.18초 · 5,442 요청/초 | 0.08초 · **12,709 요청/초** | 2.3 | 0 |
| 4 | 2,000 | 0.42초 · 4,762 요청/초 | 0.22초 · 9,269 요청/초 | 1.9 | 0 |
| 20 | 4,000 | 0.84초 · 4,773 요청/초 | 0.44초 · 9,101 요청/초 | 1.9 | 0 |

**어디서 시간을 쓰나 (cProfile · 측정)**

| 항목 | 시간 |
|---|---|
| 저장소 명령 한 번 (`get`, 락 포함) | 약 2.2µs — 그중 FNV-1a 해시 약 0.5µs |
| HTTP 요청 한 번 (새 연결) | 약 170 ~ 180µs |
| 서버 쪽 처리 중 가장 큰 것 | 요청 헤더 해석 (표준 라이브러리가 `email` 파서를 씀), 소켓 쓰기 |

**해석**
- 새 연결 방식은 클라이언트가 늘어도 **약 5,000 요청/초에서 그대로**입니다. 병목은 저장소 락이 아니라 **파이썬의 HTTP 처리 자체**(연결 · 스레드 생성, 요청 줄 · 헤더 파싱, JSON)이고, 이 코드는 GIL(9-2) 때문에 한 번에 한 스레드만 파이썬 코드를 실행합니다.
- 연결을 재사용하면 연결 · 스레드를 만드는 비용이 사라져 **약 1.9 ~ 2.3배**가 됩니다. 클라이언트가 여럿이면 GIL 을 나눠 써서 1개일 때보다 낮습니다.
- 해시 함수를 아무리 빠르게 해도 요청 시간의 1% 밖이라 손대지 않았습니다 (7-3).
- 이 측정은 클라이언트도 같은 파이썬 프로세스라 클라이언트 비용이 섞여 있습니다. 절대값보다 "방식 사이의 차이 · 클라이언트 수가 늘어도 오류 없이 처리량이 유지된다" 를 보는 측정입니다.
- 연결 대기열을 고치기 전에는 20개 동시 클라이언트에서 오류가 났습니다 (9-6).
- 캐시 데모(8-1)의 숫자는 그대로입니다: 데모 API(dev 파일)가 `urlopen` 으로 요청마다 새 연결을 열기 때문입니다.

### 8-4. 측정할 때 주의한 것

| 주의 | 한 일 |
|---|---|
| 첫 요청이 느린 것(MISS · 캐시 비어 있음)을 숨기지 않기 | 벤치마크 평균에 첫 MISS 를 포함하고 그렇게 표에 적음 |
| 헤더만 받고 재면 빠르게 보임 | 본문까지 다 읽은 시간 |
| 한 번 잰 값은 흔들림 | 연산 속도는 세 번 중 가장 빠른 값, 벤치마크는 여러 번 돌려 범위(17.7 ~ 18.6배)를 적음 |
| 출력 비용이 섞임 | 서버의 요청 로그(`log_message`)를 끔 |
| 네트워크 지연이 없음 | 같은 컴퓨터(`127.0.0.1`)라 실제 네트워크보다 빠름 — 실제 서비스면 HTTP 왕복이 더 길어지고 캐시 효과는 원본 지연에 따라 달라짐 |

## 9. 동시성 내부 원리

### 9-1. 어떤 스레드들이 동시에 도나

| 스레드 | 몇 개 | 하는 일 | 저장소를 만지나 |
|---|---|---|---|
| 메인 | 1 | `serve_forever()` — 새 연결을 받아 요청 스레드를 만듦 | 아니오 |
| 요청 스레드 | 연결마다 1 (`ThreadingHTTPServer`) | 그 연결의 요청을 하나씩 읽고 처리하고 응답 (연결을 재사용하면 여러 개, 10초 쉬면 닫음) | **예** |
| 정리 스레드 | 1 | 1초마다 `sweep()` | **예** |
| 스냅샷 스레드 | 1 (`main()` 으로 켰을 때) | 60초마다 `dump()` → 파일 | **예** (읽기) |

요청 스레드는 데몬이라 서버가 끝날 때 붙잡지 않고, 정리 · 스냅샷 스레드는 `threading.Event` 로 "그만" 신호를 받으면 `wait()` 에서 바로 깨어나 끝납니다 (최대 1초 · 60초를 기다리지 않음).

### 9-2. 파이썬에는 GIL 이 있는데 왜 락이 필요한가

파이썬(CPython)의 **GIL**(전역 인터프리터 락)은 한 순간에 한 스레드만 파이썬 바이트코드를 실행하게 합니다. 그래서 `list.append` 같은 **한 동작**은 중간에 끊기지 않습니다.
하지만 GIL 은 **몇 줄에 걸친 동작 묶음**을 지켜 주지 않습니다. 스레드는 바이트코드 사이 아무 곳에서나 바뀔 수 있고, 우리 해시 테이블의 `set` 은 "칸 찾기 → 같은 키 확인 → 붙이기 → 개수 늘리기 → 리사이즈" 로 여러 단계입니다. 그 사이에 다른 스레드가 끼면 자료구조가 틀어집니다.

### 9-3. 락이 없으면 깨지는 장면

**① 리사이즈 중 저장이 사라짐**

```
스레드 A: set("x") → 7번째 항목 → _resize 시작: 새 16칸을 만들고 옛 칸들을 옮기는 중
스레드 B: set("y") → 아직 옛 8칸에 "y" 를 붙이고 _size += 1
스레드 A: 옮기기 끝 → self._buckets = 새 16칸          ← "y" 는 옛 칸에만 있어 사라짐, _size 는 1 많음
```

**② 확인한 뒤 쓰기 (check-then-act)**

```
스레드 A: expire("k", 60) → _alive("k") 는 True (살아 있음)
스레드 B: delete("k")      → 지움
스레드 A: _expires.set("k", …)   ← 값은 없는데 만료 시각만 남은 고아 항목
```

**③ 두 번 나눠 읽기**

```
스레드 A: get("k") → "값"
스레드 B: delete("k")
스레드 A: ttl("k") → -2        ← 응답 {"value": "값", "ttl": -2} 모순
```

### 9-4. 락 설계

```python
self._lock = threading.Lock()

def expire(self, key, ttl):
    _check_ttl(ttl)              # 공유 상태를 안 만지는 검사는 락 밖에서
    with self._lock:             # 여기부터 끝까지 다른 스레드는 저장소에 못 들어옴
        if not self._alive(key):
            return False
        self._expires.set(key, self._clock() + ttl)
        return True
```

| 규칙 | 이유 |
|---|---|
| **락 하나**가 두 해시 테이블 전체를 지킴 | `_data` 와 `_expires` 는 항상 함께 바뀌어야 한다 (한쪽만 바뀐 순간을 아무도 못 보게) |
| **공개 메서드 10개 모두** `with self._lock` (`set` · `get` · `get_with_ttl` · `delete` · `exists` · `expire` · `ttl` · `sweep` · `dump` · `len`) | 9-3 의 세 장면이 모두 "확인과 쓰기 사이" 에 끼어드는 문제라, 명령 하나를 통째로 감싼다 |
| 내부 함수(`_alive` · `_ttl_left` · `_remove`)는 락을 **안 잡음** — 락을 잡은 메서드 안에서만 부름 | `threading.Lock` 은 같은 스레드가 다시 잡으면 영원히 기다린다(교착). 바깥에서 한 번만 잡는다 |
| ttl 검사는 락 **밖** | 공유 상태를 안 만지므로 락이 필요 없고, 틀리면 아무것도 안 바뀐 채 끝난다 |
| `HashTable` 자체에는 락 **없음** | 혼자 쓸 때는 필요 없고, 동시성은 위 계층(저장소)의 책임으로 나눴다 |
| `dump()` 도 락 안에서 한 번에 | 스냅샷이 "한 시점의 사진" 이 된다 (저장 도중 수정이 섞이지 않음) |

실제 Redis 도 명령을 **한 스레드에서 하나씩** 처리합니다. 락 하나로 "한 번에 명령 하나" 를 만든 것은 같은 효과입니다.

### 9-5. 락이 병목이 아닌 이유 (측정)

- 저장소 명령 한 번은 락을 잡는 시간까지 약 **2µs** (8-2).
- HTTP 요청 한 번은 새 연결이면 약 **180µs**, 연결을 재사용하면 약 **80µs** (8-3, 클라이언트 1개).
- 즉 요청 시간의 약 **1 ~ 3%** 만 락 안에 있습니다. 클라이언트를 1 → 20 으로 늘려도 처리량이 늘지 않는 것은, 락 대기가 아니라 파이썬 HTTP 처리와 GIL 이 한계이기 때문입니다.
- 락이 진짜 병목이 되면(초당 수만 요청) 칸 범위별로 락을 나누는 방법이 있습니다 (코드에 `shortcut:` 주석).

### 9-6. 운영체제 수준의 동시성

| 장치 | 값 | 없으면 생기는 일 |
|---|---|---|
| 연결 대기열 (`request_queue_size`) | **128** | 표준 기본값 5 로는 클라이언트 20개가 한꺼번에 접속할 때 넘친 연결을 운영체제가 강제로 끊었다 — 검증에서 요청 1만 개 중 **3,869개** `Connection reset`. 128 로 늘린 뒤 0개 |
| 연결마다 읽기 제한 (`REQUEST_TIMEOUT`) | 10초 → 408 | 본문을 덜 보내고 멈춘 클라이언트가 요청 스레드를 영원히 붙잡는다. 이런 연결이 쌓이면 서버가 멈춘다. 연결을 재사용하는 클라이언트가 10초 동안 다음 요청을 안 보내도 이 제한으로 닫힌다 |
| `TCP_NODELAY` | 켬 | 연결을 재사용할 때 응답 두 조각(헤더 · 본문) 중 뒤 조각이 상대 ACK 를 기다리느라 요청마다 최대 40ms 멈출 수 있다 (Linux) |
| 413 전에 본문 버리기 | 최대 16MB | 안 읽고 닫으면 운영체제가 RST 를 보내 클라이언트가 413 을 못 받는다 |
| 종료 신호 (`threading.Event`) | — | `time.sleep(60)` 이면 끌 때 최대 60초를 기다린다 |

## 10. HTTP API

요청 · 응답 본문은 모두 JSON 입니다. 키에 `/` · 한글 같은 문자가 있으면 URL 인코딩해서 보냅니다 (예: `메이플/a` → `%EB%A9%94%EC%9D%B4%ED%94%8C%2Fa`).

| 요청 | 하는 일 | 성공 응답 |
|---|---|---|
| `PUT /keys/{key}` body `{"value": 값, "ttl": 초}` | 저장 (`ttl` 은 선택, 소수 가능 · 최소 0.001초) | `200 {"ok": true}` |
| `GET /keys/{key}` | 조회 | `200 {"key": k, "value": v, "ttl": n}` |
| `DELETE /keys/{key}` | 삭제 (캐시 무효화) | `200 {"deleted": true \| false}` |
| `GET /keys/{key}/ttl` | 남은 만료 시간 | `200 {"ttl": 초}` — 만료 없음 `-1`, 키 없음 `-2` |
| `POST /keys/{key}/expire` body `{"ttl": 초}` | 만료 시간 설정 | `200 {"ok": true}` |
| `GET /health` | 상태 확인 | `200 {"keys": 저장된 키 수}` |

**규칙 (실제 Redis 와 같게)**
- 만료된 키는 절대 응답으로 나가지 않습니다 (읽을 때 바로 지움 + 1초마다 정리).
- `ttl` 없이 같은 키에 다시 저장하면 기존 만료가 사라집니다.
- 남은 시간은 올림입니다 (0.3초 남으면 `1`).
- `value` 로 `null` 은 저장할 수 없습니다 ("없음" 과 구별이 안 되므로).

**오류 응답** — 모두 `{"error": "이유"}` 입니다.

| 상태 | 언제 | 예 |
|---|---|---|
| 400 | 잘못된 JSON · `NaN` · 객체가 아닌 본문 · `value` 없음 · 잘못된 ttl 등 | `{"error": "ttl은 0.001초 이상의 유한한 숫자여야 합니다"}` |
| 404 | 키 없음 · 만료됨 / 없는 경로 | `{"error": "키가 없습니다"}` |
| 405 | 경로는 맞는데 메서드가 다름 | `{"error": "GET / PUT / DELETE만 지원합니다"}` |
| 408 | 본문을 10초 안에 다 보내지 않음 | `{"error": "요청 본문을 제한 시간 안에 다 받지 못했습니다"}` |
| 413 | 본문이 1MB 초과 | `{"error": "요청 본문이 너무 큽니다 (최대 1MB)"}` |
| 500 | 예상 못 한 오류 (서버는 계속 동작) | `{"error": "서버 내부 오류"}` |

전체 문구 목록은 [설계.md](./설계.md) 8장에 있습니다.

**데이터 보존 (스냅샷)** — 서버를 껐다 켜도 데이터가 남습니다.

```bash
python -m mini_redis.server --port 6380 --snapshot data/dump.json --snapshot-interval 60
```

- 위 값이 기본값이라 그냥 `python -m mini_redis.server` 만 해도 됩니다. 켤 때 복구하고, 60초마다 + Ctrl+C 로 끌 때 저장합니다.
- ttl 이 있는 키는 **꺼져 있던 시간만큼 줄어서** 복구됩니다. 그 사이 만료된 키는 복구하지 않습니다.
- 파일이 손상돼 있으면 서버가 **시작을 거부**합니다. 저장을 끄려면 `--snapshot ""`.

**예시**

```bash
curl -X PUT localhost:6380/keys/session:42 -d '{"value": {"user": "철수"}, "ttl": 1.5}'
curl localhost:6380/keys/session:42/ttl
curl -X POST localhost:6380/keys/session:42/expire -d '{"ttl": 30}'
curl -X DELETE localhost:6380/keys/session:42
curl localhost:6380/health
```

## 11. 파이썬에서 바로 쓰기

HTTP 없이 저장소만 쓸 수도 있습니다.

```python
from mini_redis.store import MiniRedis

r = MiniRedis()
r.set("user:1", {"name": "철수"}, ttl=60)
r.get("user:1")           # {'name': '철수'}
r.ttl("user:1")           # 60
r.get_with_ttl("user:1")  # ({'name': '철수'}, 60) — 값과 ttl 을 한 번에
r.delete("user:1")        # True
r.ttl("user:1")           # -2 (키 없음)
```

여러 스레드에서 동시에 써도 안전합니다 (9장). 테스트에서는 `MiniRedis(clock=가짜_시계)` 로 시간을 기다리지 않고 흘릴 수 있습니다.

## 12. 캐시 데모

느린 원본(0.2초 걸리는 DB 흉내) 앞에 Mini Redis 를 캐시로 붙인 예제 API 입니다.

```bash
python -m mini_redis.server --port 6380
```

```bash
python -m demo.api_server --port 8000 --redis http://127.0.0.1:6380
```

```bash
curl localhost:8000/items/1
```

| 요청 | 결과 |
|---|---|
| `GET /items/1` 처음 | `"cache": "MISS"` — 원본을 읽고(0.2초) 캐시에 60초 저장 |
| `GET /items/1` 다시 | `"cache": "HIT"` — 캐시에서 바로 (약 1ms) |
| `GET /items/1?cache=off` | `"cache": "OFF"` — 매번 원본 |
| `PUT /items/1` body `{"price": 5}` | 원본 수정 + 버전을 올려 옛 캐시를 무효화 |
| Mini Redis 가 꺼져 있을 때 | `"cache": "BYPASS"` — 원본으로라도 응답 |

**버전 키가 막는 경쟁 상태** — "수정한 뒤 캐시 삭제" 만 하면:

```
요청 A (GET) : 원본에서 가격 100 읽음 ─── (0.2초 걸림) ───▶ 캐시에 100 저장!
요청 B (PUT) :          가격을 5 로 수정 → 캐시 삭제
결과         : 이후 60초 동안 옛 가격 100 이 HIT 로 나감
```

캐시 키가 `item:{id}:v{버전}` 이면 B 가 버전을 올린 순간 옛 키는 아무도 읽지 않고, A 의 옛 데이터는 저장 전 버전 확인에 걸려 저장되지도 않습니다.

## 15. 한계

| 한계 | 설명 |
|---|---|
| 자료형 | 문자열 키 → JSON 값 하나만. Redis 의 List · Set · Hash 등은 없음 |
| 프로토콜 | Redis 의 RESP 가 아니라 HTTP JSON |
| 속도 | 해시 계산이 파이썬 반복문이라 `dict` 보다 약 47배 느림 (명령 한 번 약 2µs). HTTP 처리량은 새 연결 약 5,000 · 연결 재사용 약 9,000 ~ 12,700 요청/초 (8장). 연결을 재사용하는 클라이언트 하나가 스레드 하나를 쥐고 있어, 쉬는 연결이 아주 많으면 스레드도 그만큼 (10초 뒤 닫힘) |
| 영속성 | 스냅샷 방식이라, 서버가 갑자기 죽으면(전원 · `kill -9`) 마지막 저장 뒤 최대 60초치 변경을 잃음. AOF(명령 기록)는 없음 |
| 메모리 | 한도 · LRU 제거 없음. 해시 테이블은 커지기만 하고 줄지 않음 |
| 규모 | 락 하나 · 1초마다 만료 키 전부 훑기 — 초당 수만 요청 · 만료 키 수십만 개를 넘으면 바꿔야 함 (`shortcut:` 주석) |
| 데모 서버 | `demo/api_server.py`(dev 파일)는 연결 대기열이 기본값 5 라, 클라이언트 수십 개가 한꺼번에 접속하면 일부 연결이 끊김. Mini Redis 서버는 고쳤음 (9-6) |
