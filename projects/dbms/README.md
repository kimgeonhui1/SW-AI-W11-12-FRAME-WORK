# Mini DBMS

SQL 처리기, B+ 트리 인덱스, 스레드 풀 API 서버를 **Python 표준 라이브러리만으로** 직접 만든 미니 DBMS입니다.

| Phase | 내용 |
|---|---|
| 1 | SQL 파일을 읽어 `INSERT` · `SELECT` 실행, 데이터는 파일에 저장 |
| 2 | 메모리 기반 B+ 트리 인덱스, 자동 `id`, 100만 행에서 인덱스 검색 vs 전체 탐색 비교 |
| 3 | 스레드 풀로 요청을 처리하는 HTTP API 서버, 동시성 벤치마크 |

- 외부 라이브러리 0개 (Python 3.9 이상)
- 단위 테스트 116개

---

## 실행

모든 명령은 `projects/dbms` 폴더에서 실행합니다.

```powershell
python -m minidb examples/demo.sql                  # Phase 1: SQL 파일 실행 (DB 폴더 기본값: data)
python -m minidb.server --port 8080                 # Phase 3: API 서버 (작업자 8개, 큐 64칸)
python -m minidb.bench                              # Phase 2: 100만 행 인덱스 vs 전체 탐색 (수 분 걸림)
python -m minidb.bench_server                       # Phase 3: 서버 동시성 벤치마크
python -m unittest discover -s tests -t .           # 테스트 전체
```

서버에 요청 보내기 (PowerShell):

```powershell
Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8080/query -ContentType 'application/json' -Body '{"sql": "SELECT * FROM users WHERE id = 1"}'
```

### 지원하는 SQL

```sql
INSERT INTO users (name, age) VALUES ('홍길동', 25);   -- id는 자동으로 부여 (직접 넣으면 오류)
INSERT INTO users VALUES ('it''s me', 30);              -- 컬럼 목록 생략 시 스키마 순서
SELECT * FROM users WHERE id = 1;                       -- id 조건 → B+ 트리 인덱스
SELECT name, age FROM users WHERE name = '홍길동';      -- 다른 열 조건 → 전체 탐색
CREATE TABLE books (title TEXT, price INT);             -- 테이블 추가 (id 열은 자동)
```

- 테이블은 `data/schema.json`에 정의합니다. `CREATE TABLE`은 이 파일에 테이블을 더합니다.
  - 임시 파일에 쓴 뒤 `os.replace`로 한 번에 바꿔서, 저장 도중 꺼져도 기존 스키마가 깨지지 않습니다.
  - 이미 있는 이름, 대소문자만 다른 이름, 같은 컬럼 두 번, `id` 컬럼 직접 정의, 스키마에 없는 예전 데이터 파일(`books.jsonl`)이 남아 있는 경우는 거절합니다.
  - API 서버에서는 CREATE끼리만 스키마 락을 잡습니다. 테이블 락을 테이블보다 먼저 등록하고, 락이 없는 테이블은 실행기에 넘기지 않아서 INSERT가 락 없이 실행될 틈이 없습니다.
- 타입은 `INT`(64비트 정수)와 `TEXT`입니다.
- `WHERE`는 `열 = 값` 하나만 지원합니다.
- 키워드는 대소문자를 가리지 않습니다. `--` 주석을 쓸 수 있습니다.

## 구조

```
SQL 문자열
  → tokenizer.py   정규식 하나로 토큰 분리 (문자열 · 숫자 · 이름 · 기호, 줄 · 칸 위치 기록)
  → parser.py      재귀 하강 파서 → Insert / Select 객체
  → executor.py    스키마 검사, 실행 계획 선택 (WHERE id → 인덱스, 그 외 → 전체 탐색)
  → storage.py     테이블마다 JSON Lines 파일 + B+ 트리 (id → 파일 안 위치)
```

| 파일 | 역할 |
|---|---|
| `minidb/cli.py` | Phase 1 입구. 결과를 표로 출력 |
| `minidb/bptree.py` | B+ 트리 (검색 · 삽입 · 분할 · 일괄 생성) |
| `minidb/rwlock.py` | 읽기-쓰기 락 |
| `minidb/threadpool.py` | 스레드 풀 (작업 큐 + 작업자 N개) |
| `minidb/engine.py` | 서버용 실행 엔진. 테이블마다 락을 잡고 SQL 실행 |
| `minidb/server.py` | HTTP API 서버 |
| `minidb/bench.py`, `minidb/bench_server.py` | 벤치마크 |

## Phase 1 · SQL 처리기와 파일 저장

- **파싱을 먼저 전부 끝냅니다.** 문법 오류가 하나라도 있으면 아무 문장도 실행하지 않습니다. 파일의 절반만 실행되는 일을 막기 위해서입니다.
- **오류 위치를 알려 줍니다.** 예: `문법 오류: INSERT 또는 SELECT 문장이어야 합니다 ... (줄 1, 칸 1)`
- **저장 형식은 JSON Lines입니다.** 테이블마다 파일 하나(`data/users.jsonl`)에 행을 한 줄씩 덧붙입니다. 문자열 안의 쉼표 · 따옴표 · 줄바꿈도 JSON이 안전하게 처리합니다.
- **스키마를 검사합니다.** 없는 테이블 · 열, 타입이 다른 값, 64비트를 넘는 정수는 실행 전에 거절합니다.

## Phase 2 · B+ 트리 인덱스

- **자동 id**: INSERT마다 `id = 지금까지의 최대값 + 1`을 부여합니다.
- **인덱스 내용**: B+ 트리에 `id → 그 행이 파일의 몇 번째 바이트에서 시작하는지`를 저장합니다. `WHERE id = 값`은 트리에서 위치를 찾아 그 한 줄만 읽습니다 (O(log n)).
- **트리 모양**: order 64(노드 하나에 키 최대 63개)입니다. 100만 행이면 높이 4입니다.
- **분할 방식**:
  - 리프 노드가 넘치면 오른쪽 노드의 첫 키를 부모에 **복사**합니다.
  - 내부 노드가 넘치면 가운데 키를 부모로 **올립니다**.
- **순서대로 들어오는 id 최적화**: id는 항상 커지는 순서로 들어옵니다. 그래서 맨 오른쪽 노드가 넘치면 반반 나누지 않고 왼쪽을 가득 채웁니다. 리프가 거의 100% 차서 같은 데이터에 노드 수가 절반 가까이 줄어듭니다.
- **재시작**: 인덱스는 메모리에만 있습니다. DB를 다시 열면 파일을 한 번 읽고, 정렬된 id로 트리를 아래에서 위로 한 번에 쌓습니다(bulk load).

## Phase 3 · 스레드 풀 API 서버

```
접속 스레드 (accept)  →  작업 큐 (기본 64칸)  →  작업자 스레드 N개 (기본 8)  →  Engine (테이블별 읽기-쓰기 락)
                         큐가 꽉 차면 바로 503
```

- **스레드 풀**: 연결마다 스레드를 새로 만들지 않습니다. 정해진 수의 작업자가 큐에서 연결을 꺼내 처리합니다.
- **과부하 처리**: 큐가 꽉 차면 기다리게 하지 않고 바로 `503`으로 거절합니다. 서버가 무너지는 대신 받은 요청은 끝까지 처리합니다.
- **락**:
  - SELECT는 읽기 락이라 여러 개가 동시에 실행됩니다.
  - INSERT는 쓰기 락이라 혼자 실행됩니다. id가 겹치거나 파일이 섞이지 않게 하기 위해서입니다.
  - 쓰기를 기다리는 요청이 있으면 새 읽기를 먼저 들여보내지 않습니다(writer 우선). 쓰기가 계속 밀리는 것을 막기 위해서입니다.
  - SQL 파싱은 락 밖에서 합니다.
- **API**

  | 요청 | 응답 |
  |---|---|
  | `GET /health` | `200 {"status": "ok"}` |
  | `POST /query` `{"sql": "..."}` | `200 {"results": [{"columns", "rows", "message", "plan"}]}` |
  | 문법 오류 | `400` (아무것도 실행 안 함) |
  | 실행 오류 | `400` + 앞 문장까지의 `results` |

- **잘못된 요청 방어**:

  | 상황 | 응답 |
  |---|---|
  | Content-Length 없음 · 중복 · 숫자 아님 | `400` |
  | chunked 전송 | `411` |
  | 본문 1MB 초과 | `413` |
  | 10초 안에 본문을 다 안 보냄 | `408` |
  | 본문을 보내다 연결이 끊김 | `400` |
  | 깨진 JSON | `400` |

- **응답 후 연결 닫기 (lingering close)**: 본문을 읽지 않고 답한 경우가 있습니다(본문이 붙은 404 · 405, 503). 이때 바로 닫으면 Windows가 RST를 보내 클라이언트가 응답을 못 받습니다. 그래서 쓰기 방향을 먼저 닫고 남은 데이터를 최대 0.5초(503은 0.2초) 읽어 버린 뒤 닫습니다.

## 성능 결과

측정 환경: Windows 11, Python 3.14, 한 대의 PC에서 한 번 실행한 값입니다. 실행마다 조금씩 다릅니다.

### Phase 2 · 100만 행 (`python -m minidb.bench`)

| 항목 | 결과 |
|---|---|
| `WHERE id = 값` (B+ 트리) | p50 **0.17ms** |
| `WHERE name = 값` (전체 탐색) | 약 **4.2~4.8초** |
| 100만 행 INSERT (Phase 1 처리기 그대로 사용) | 62.6초 |
| 재시작 시 인덱스 다시 만들기 | 5.7초 |
| 트리 높이 / 인덱스 메모리 | 4 / 약 79MB |

인덱스 검색이 전체 탐색보다 **2만 배 이상** 빠릅니다. 세 가지 검색 방법(인덱스, 인덱스 끈 id 탐색, name 탐색)의 결과 행이 같은지도 함께 확인합니다.

### Phase 3 · 서버 동시성 (`python -m minidb.bench_server`, 5만 행)

| 동시 클라이언트 | id SELECT 요청/초 | INSERT 요청/초 |
|---:|---:|---:|
| 1 | 848 (p95 1.8ms) | 526 |
| 4 | 1,430 | 1,291 |
| 16 | 1,678 (p95 11.9ms) | 1,368 |

- **작업자 수 비교** (클라이언트 16명): 작업자 1개 1,545 요청/초, 작업자 8개 1,669 요청/초.
- **과부하** (작업자 2개 · 큐 4칸에 느린 전체 탐색 90건): `503` 62건, `200` 28건, 연결 오류 0건. 감당 못 하는 요청은 바로 거절하고, 받은 요청은 끝까지 처리합니다.

작업자를 늘려도 처리량이 크게 늘지 않는 이유는 Python의 GIL입니다. GIL 때문에 CPU 작업(파싱 · JSON · 트리 탐색)은 한 번에 하나만 실행되고, 네트워크와 파일 대기만 겹칩니다.

## 검증

- **단위 테스트 116개**: 토크나이저, 파서, 실행기, 저장소, B+ 트리 불변식, 락 · 스레드 풀 동시성, 서버(실제 HTTP 요청), 벤치마크, CREATE TABLE.
- **변이 테스트**: 락과 B+ 트리 코드를 일부러 망가뜨려 테스트가 잡아내는지 확인했습니다.
- **교차 검증**: 다른 AI(GPT · Gemini)의 리뷰를 받았습니다. 지적은 그대로 받지 않고, 직접 재현되는 것만 고쳤습니다.

## 한계

- **인덱스가 메모리에만 있음**: 재시작할 때마다 파일을 읽어 다시 만듭니다 (100만 행에 약 6초).
- **fsync 안 함**: 정전 시 마지막 쓰기가 사라질 수 있습니다.
- **GIL**: 작업자를 늘려도 CPU 작업은 병렬로 실행되지 않습니다.
- **HTTP/1.0만 지원**: 요청 하나마다 연결 하나를 씁니다.
- **아직 없는 기능**: `DELETE`, `UPDATE`, `DROP TABLE`, 범위 검색, `AND` · `OR` 조건.
