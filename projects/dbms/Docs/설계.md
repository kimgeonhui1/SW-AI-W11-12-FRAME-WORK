> 언어: **Python 3.10 이상, 표준 라이브러리만** (Mini Redis 와 같은 방식 · 설치할 것 없음 · 테스트는 `unittest`)

## 0. 한 줄 요약

텍스트 파일의 SQL 을 **읽고(토큰) → 구조로 바꾸고(파서) → 실행(실행기) → 파일에 저장(저장소)** 하는 처리기를 만들고(Phase 1),
`id` 에 **B+ 트리 인덱스**를 붙여 100만 건에서 인덱스 / 선형 탐색 속도를 비교하고(Phase 2),
이 둘을 엔진으로 두고 **스레드 풀 HTTP API 서버**로 감싼다(Phase 3).

| 단계 | 결과물 | 끝났다고 말할 기준 |
|---|---|---|
| Phase 1 | `python -m mini_dbms queries.sql` 로 INSERT / SELECT 가 동작하는 파일 기반 처리기 | 기능 테스트(SQL 파일 → 기대 출력) 통과, 잘못된 SQL 은 줄 · 칸 번호가 있는 오류 |
| Phase 2 | Phase 1 처리기 + 메모리 B+ 트리 (`id`) + 100만 건 벤치마크 | B+ 트리 불변식 검사 통과, `WHERE id = ?` 가 인덱스를 쓰는지 테스트로 확인, 속도 비교표 |
| Phase 3 | `POST /query` 로 SQL 을 받는 API 서버 + 스레드 풀 | 클라이언트 수십 개 동시 요청에서 결과가 맞고, 읽기는 병렬 · 쓰기는 안전 |

## 1. 요구사항 정리 (과제 → 이 프로젝트에서의 뜻)

| 과제 문장 | 이렇게 해석 · 결정 |
|---|---|
| SQL 문을 텍스트 파일로 CLI 에 전달 | `python -m mini_dbms <파일.sql>` · 한 파일에 문장 여러 개(`;` 로 구분) · `-e "SQL"` 로 한 문장 · 인자 없으면 대화형(REPL) |
| 최소 INSERT · SELECT | 이 둘만 확실히. 그 밖의 문장(UPDATE · DELETE · CREATE)은 "지원하지 않는 문장" 오류 |
| 각 테이블은 파일로 관리 | 테이블 하나 = 스키마 파일 하나 + 데이터 파일 하나 (3장) |
| 저장 포맷 자유 | **JSON Lines** (한 줄 = 한 행 = JSON 배열). 이유는 3-2 |
| schema · table 은 이미 존재 | `data/<테이블>.schema.json` 을 미리 만들어 둔다 (예제 테이블 + 만드는 스크립트). CREATE TABLE 은 만들지 않는다 |
| 레코드 추가 시 ID 자동 부여 | 모든 테이블의 첫 열은 `id INT` (자동). INSERT 에서 `id` 를 직접 주면 오류 |
| ID 를 B+ 트리에 등록 | 키 = `id`, 값 = 데이터 파일 안의 **바이트 위치(offset)** → 찾으면 그 줄만 바로 읽는다 |
| 메모리 기반 B+ 트리 | 인덱스는 메모리에만. 서버 · CLI 가 켤 때 데이터 파일을 한 번 훑어 다시 만든다 (4-4) |
| 100만 건 이상 INSERT | Phase 1 의 SQL 처리기를 그대로 통해 넣는다 (여러 행 INSERT 1,000행씩) (5장) |
| ID SELECT vs 다른 필드 SELECT 비교 | `WHERE id = ?` (인덱스) vs `WHERE name = ?` (선형 탐색) 시간 비교표 (5장) |
| 스레드 풀 · 요청마다 스레드 할당 · 병렬 처리 | `concurrent.futures.ThreadPoolExecutor` 에 연결을 넘기는 HTTP 서버 (6장) |
| Phase 1 + 2 를 그대로 활용 | 서버는 `Engine.execute(sql)` 하나만 부른다. 파서 · 실행기 · 인덱스는 CLI 와 같은 코드 |

## 2. 전체 구조

```
               ┌───────────── 입구 (둘 다 같은 Engine 을 부른다) ─────────────┐
 SQL 파일 / -e │  cli.py  (Phase 1)                server.py  (Phase 3)        │ HTTP JSON
 ─────────────▶│  파일 읽기 · 결과 표 출력          스레드 풀 · 요청 검사 · JSON  │◀──────────
               └───────────────────────────┬──────────────────────────────────┘
                                           ▼
                  engine.py   Engine.execute(sql) → [결과, …]     ← 유일한 공개 진입점
                                           │
          ┌────────────────────────────────┼────────────────────────────────┐
          ▼                                ▼                                ▼
   tokenizer.py  SQL 글자 → 토큰    parser.py  토큰 → 문장 객체(AST)   executor.py  문장 → 실행 계획 → 결과
                                                                            │
                                                     ┌──────────────────────┼─────────────────────┐
                                                     ▼                      ▼                     ▼
                                              catalog.py  스키마      table.py  데이터 파일      bptree.py  B+ 트리
                                              (열 이름 · 타입)        (추가 · 위치로 읽기 · 훑기)  (id → 파일 위치)
```

| 계층 | 아는 것 | 모르는 것 |
|---|---|---|
| 입구 (cli · server) | 입력 받기 · 출력 형식 · HTTP · 스레드 풀 | SQL 문법 · 파일 형식 |
| Engine | 문장을 순서대로 실행 · 테이블 락 | HTTP · 출력 형식 |
| SQL (tokenizer · parser) | 문법 | 파일 · 인덱스 |
| 실행기 | 계획 고르기(인덱스 / 훑기) · 조건 평가 · 타입 검사 | 바이트 형식 |
| 저장 (catalog · table · bptree) | 파일 형식 · 인덱스 구조 | SQL |

계층을 나누는 이유: Phase 2 는 저장 계층에 인덱스만 더하고, Phase 3 은 입구만 하나 더 붙인다. **아래 계층을 고치지 않고 위에 쌓는 구조**가 과제의 "그대로 활용" 이다.

## 3. Phase 1 — SQL 처리기

### 3-1. 지원할 SQL (문법)

```
문장들     := 문장 (";" 문장)* ";"?
INSERT     := INSERT INTO 테이블 [ "(" 열, … ")" ] VALUES "(" 값, … ")" ( "," "(" 값, … ")" )*
SELECT     := SELECT ( "*" | 열, … ) FROM 테이블 [ WHERE 조건 ] [ ORDER BY 열 [ASC|DESC] ] [ LIMIT 정수 ]
조건       := 비교 ( AND 비교 )*
비교       := 열 연산자 값      연산자: =  !=  <>  <  <=  >  >=
값         := 정수 | 소수 | '문자열' | NULL
```

| 규칙 | 결정 |
|---|---|
| 키워드 | 대소문자 무시 (`select` = `SELECT`). 테이블 · 열 이름은 소문자로 맞춤 |
| 문자열 | 작은따옴표. 안의 `'` 는 `''` 로 (SQL 표준). 한글 · 이모지 그대로 |
| 주석 | `-- 한 줄`, `/* 여러 줄 */` |
| 여러 행 INSERT | `VALUES (…), (…)` — 100만 건 넣을 때 문장 수를 줄이는 핵심 |
| 열 목록 생략 INSERT | 스키마 순서대로 (`id` 제외) |
| 꼭 만들 것 / 여유 있으면 | **꼭**: INSERT · SELECT `*` / 열 · WHERE 비교 하나 · AND. **여유**: ORDER BY · LIMIT · `EXPLAIN` · `COUNT(*)` (8장) |

`OR` · 괄호 조건 · JOIN · GROUP BY 는 하지 않는다 (요구사항 밖, 계획 고르기를 단순하게 유지).

### 3-2. 저장 형식 — 왜 JSON Lines 인가

```
data/users.schema.json   {"columns": [{"name": "id", "type": "INT"}, {"name": "name", "type": "TEXT"}, {"name": "age", "type": "INT"}]}
data/users.jsonl         [1,"김준우",25]
                         [2,"O'Brien",null]
                         [3,"줄바꿈\n있음",30]
```

| 후보 | 장점 | 문제 |
|---|---|---|
| CSV | 사람이 읽기 쉬움 | 값 안의 쉼표 · 따옴표 · **줄바꿈** 처리가 까다롭고, 줄바꿈이 든 값이 있으면 "한 줄 = 한 행" 이 깨져 offset 으로 한 줄만 읽을 수 없다. 타입(숫자 / 문자열 / NULL)이 사라짐 |
| 바이너리 고정 길이 | offset 계산이 산수, 가장 빠름 | 가변 길이 문자열을 다루려면 별도 영역이 필요 — 코드가 크게 늘어남 |
| **JSON Lines** (선택) | `json.dumps` 가 줄바꿈 · 따옴표를 이스케이프 → **항상 한 줄 = 한 행**. 숫자 / 문자열 / null 타입 유지. 표준 라이브러리로 끝 | CSV 보다 조금 큼 |

- **추가(INSERT)**: 파일 끝에 줄을 붙인다(`append`). 붙이기 전 위치(`f.tell()`)가 그 행의 offset → B+ 트리에 `id → offset`.
- **id 로 읽기**: `seek(offset)` → `readline()` 한 번.
- **훑기(선형 탐색)**: 처음부터 줄마다 `json.loads`.
- **파일 끝이 깨진 경우** (쓰다가 꺼짐): 켤 때 마지막 줄이 JSON 으로 안 읽히면 그 줄을 잘라 내고 경고 (데이터 손실을 숨기지 않음).
- 쓰기는 `flush()` 까지. `fsync` 는 옵션(`--sync`) — 100만 건에서 매번 하면 너무 느리다 (보고서에 측정해서 적기).

### 3-3. 처리 흐름

```
"INSERT INTO users (name, age) VALUES ('kim', 25);"
  ─ tokenizer ─▶ [INSERT, INTO, IDENT(users), "(", IDENT(name), ",", IDENT(age), ")", VALUES, "(", STRING(kim), ",", INT(25), ")", ";"]
  ─ parser    ─▶ Insert(table="users", columns=["name","age"], rows=[["kim", 25]])
  ─ executor  ─▶ ① 테이블 · 열 있나 ② 타입 맞나 ③ (모든 행 검사가 끝난 뒤) id 부여 → 파일에 붙이기 → 인덱스 등록
  ─ 결과      ─▶ {"type": "insert", "count": 1, "ids": [1]}
```

- **토크나이저는 정규식 하나**(`re.Scanner` 또는 이름 붙은 그룹 `finditer`)로 만든다. 글자 하나씩 도는 파이썬 반복문은 100만 행 SQL(수천만 글자)에서 너무 느리다.
- 토큰마다 **줄 · 칸 번호**를 들고 다녀서 오류에 위치를 적는다: `3번째 줄 18칸: 'VALUES' 가 와야 하는데 'VALUE' 가 있습니다`.
- **여러 행 INSERT 는 전부 검사한 뒤 쓴다** → 1,000행 중 하나가 틀리면 한 행도 쓰지 않는다 (반쯤 들어간 상태를 만들지 않음).
- 파일에 문장이 여러 개면 순서대로 실행하고, 틀린 문장을 만나면 **거기서 멈춘다** (앞 문장 결과는 남음 · 몇 번째 문장에서 멈췄는지 출력). `--continue` 로 계속 진행 옵션.

### 3-4. CLI

```bash
python -m mini_dbms examples/phase1.sql            # 파일의 문장을 순서대로
python -m mini_dbms -e "SELECT * FROM users WHERE id = 3"
python -m mini_dbms                                # 대화형 (mini_dbms> 프롬프트, ; 까지 입력받아 실행)
python -m mini_dbms --data ./data --format json q.sql
```

출력(기본 표):
```
+----+--------+-----+
| id | name   | age |
+----+--------+-----+
|  1 | 김준우 |  25 |
+----+--------+-----+
1 row (0.12 ms, 인덱스: id = 1)
```
- 한글 폭(동아시아 넓은 글자 = 2칸)을 맞춰 표가 어긋나지 않게 (`unicodedata.east_asian_width`).
- 종료 코드: 모두 성공 0 · SQL 오류 1 · 파일 · 인자 오류 2.

### 3-5. 오류 · 엣지 케이스 (Phase 1)

| 경우 | 동작 |
|---|---|
| 없는 테이블 / 열 | `SqlError`: `테이블 'user' 가 없습니다 (있는 테이블: users, products)` |
| 열 수 ≠ 값 수 | 오류, 그 문장은 아무것도 쓰지 않음 |
| 타입 불일치 (`age = 'x'`) | 오류. 정수 열에 소수(`25.5`)도 오류. `NULL` 은 허용 |
| `id` 직접 지정 | 오류 (자동 부여 열) |
| 닫히지 않은 문자열 · 괄호 | 줄 · 칸이 있는 오류 |
| 빈 파일 · 주석만 · `;;` | 오류 없이 실행할 문장 0개 |
| 아주 긴 문자열 · 한글 · 이모지 · `'` · 줄바꿈 | 저장 → 읽기 왕복이 같아야 함 |
| 큰 정수 (`2**63` 이상) | 오류 (INT 는 64비트 부호 있는 정수로 제한) |
| `NaN` · `Infinity` | 문법에서 받지 않음 |
| 빈 테이블 SELECT | 헤더만 + `0 rows` |
| WHERE 의 NULL 비교 | SQL 처럼 `NULL = NULL` 도 거짓 (`IS NULL` 은 여유 있으면) |

## 4. Phase 2 — B+ 트리 인덱스

### 4-1. 구조

```
                         [ 40 | 80 ]                     ← 안쪽 노드: 키 = 길잡이, 자식 포인터 n+1 개
                 ┌─────────┼──────────┐
           [10|20|30]   [40|50|60]  [80|90]              ← 잎 노드: (id, 파일 offset) 를 정렬해서
               ↓ ───────────▶ ↓ ──────────▶ ↓            ← 잎끼리 next 로 이어짐 → 범위 검색
```

| 결정 | 값 · 이유 |
|---|---|
| 차수(order) | 노드당 최대 키 **64** (생성 인자로 바꿀 수 있게). 파이썬 리스트 + `bisect` 로 노드 안 검색 → 높이는 100만 건에서 약 4 |
| 키 · 값 | 키 = `id`(정수, 겹치지 않음), 값 = offset. 같은 키 다시 넣기 = 오류 |
| 연산 | `insert(key, value)` · `search(key)` · `range(lo, hi)` (잎 연결 따라감) · `__len__` · `height()` |
| 삭제 | **하지 않음** — DELETE 문이 요구사항에 없다 (있으면 병합 · 재분배가 필요) |
| 분할 | 잎이 넘치면 반으로 나누고 오른쪽 첫 키를 부모로 **복사**, 안쪽 노드가 넘치면 가운데 키를 부모로 **올림** (루트가 넘치면 높이 +1) |
| 순서대로 들어오는 id 최적화 | id 는 항상 커지므로 대부분 맨 오른쪽 잎에 들어간다. 일반 분할은 반반이라 잎이 반만 찬다 → **맨 오른쪽 잎은 꽉 채운 뒤 새 잎을 여는** 분할(오른쪽 치우침 분할)로 노드 수 · 메모리를 약 절반으로. 일반 분할과 둘 다 구현해 메모리 · 높이 비교 (차별점) |

### 4-2. 실행기가 인덱스를 쓰는 때 (계획 고르기)

| WHERE | 계획 | 비용 |
|---|---|---|
| `id = 5` | 인덱스 한 점 찾기 → `seek` 한 번 | O(log n) |
| `id > 100 AND id <= 200` · `id BETWEEN` | 인덱스 범위 → 잎 따라가며 offset 들 → 각 줄 읽기 | O(log n + k) |
| `id = 5 AND age > 20` | 인덱스로 후보를 줄인 뒤 나머지 조건은 행에서 검사 | O(log n) |
| `name = 'kim'` · 조건 없음 · `id != 5` | 처음부터 끝까지 훑기 | O(n) |

- 계획은 결과와 함께 돌려준다 (`"plan": "index-eq id=5"` / `"full-scan"`) → CLI 마지막 줄 · API 응답 · 테스트에서 **인덱스를 실제로 썼는지** 확인한다.
- `EXPLAIN SELECT …` 로 실행하지 않고 계획만 보여 주기 (여유 있으면).

### 4-3. 검증 (B+ 트리는 테스트를 가장 많이)

- **불변식 검사 함수** `check()`: 모든 잎 깊이 같음 · 노드 안 키 정렬 · 루트 외 노드 키 수 하한(오른쪽 치우침 분할의 마지막 잎은 예외) · 안쪽 키가 자식 범위를 가름 · 잎 연결을 따라가면 전체 키가 정렬 순서로 한 번씩.
- **모델 대조**: 무작위 순서 · 순서대로 · 역순으로 수만 개 넣으며 매번 `dict` · `sorted` 와 `search` · `range` 결과 비교 + `check()`.
- 경계: 빈 트리 · 키 1개 · 정확히 차수만큼 · 차수+1 (첫 분할) · 루트 분할 · 아주 작은 차수(3)로 높은 트리.

### 4-4. 인덱스는 메모리에만 — 켤 때 다시 만들기

- 엔진이 테이블을 처음 열 때 데이터 파일을 한 번 훑어 `(id, offset)` 으로 B+ 트리를 다시 만든다. id 는 파일 순서대로 커지므로 **정렬된 채로 들어온다 → 한꺼번에 쌓기(bulk load)** 로 잎을 왼쪽부터 꽉 채워 만들 수 있다 (한 개씩 넣기보다 빠름 — 측정해서 비교).
- 다음 id = 마지막 id + 1.
- 100만 건 다시 만들기 시간을 측정해 적는다 (서버 시작 시간에 들어가므로).
- (여유) 인덱스를 파일로 저장해 두고 데이터 파일 크기 · 수정 시각이 같으면 읽기만 → 시작 시간 단축.

## 5. Phase 2 — 100만 건 성능 비교 계획

### 5-1. 데이터 만들기

```bash
python -m bench.gen_sql --rows 1000000 --batch 1000 > /tmp/users_1m.sql    # INSERT … VALUES (…) × 1000 행씩 = 1,000 문장
python -m mini_dbms --data /tmp/bench_data /tmp/users_1m.sql                # Phase 1 처리기 그대로 실행
```
- 이름 · 나이 · 이메일을 **고정 씨앗 난수**로 만든다 → 누가 돌려도 같은 데이터 · 같은 결과.
- 찾을 값(`name = 'user_777777'`)이 정확히 한 행에만 있도록 만들어, 인덱스 / 훑기가 **같은 한 행**을 찾는 공정한 비교가 되게 한다.
- 넣는 시간도 잰다 (목표: 100만 건 1분 안. 병목이 토크나이저 · `json.dumps` · 인덱스 중 어디인지 cProfile 로 나눠 적기).

### 5-2. 측정

| 쿼리 | 계획 | 반복 |
|---|---|---|
| `SELECT * FROM users WHERE id = ?` (앞 · 가운데 · 끝 · 없는 id) | 인덱스 | 각 1,000번, 중앙값 · p95 |
| `SELECT * FROM users WHERE name = ?` (같은 행) | 훑기 | 각 10번, 중앙값 |
| `SELECT * FROM users WHERE id BETWEEN ? AND ?` (1,000행) | 인덱스 범위 | 100번 |
| 같은 범위를 `age` 로 | 훑기 | 10번 |

- 파싱 시간은 빼지 않고(사용자가 보는 시간) 함께 적되, **엔진 실행 시간만** 따로도 적는다.
- 데이터 크기를 1만 · 10만 · 100만으로 바꿔 **인덱스는 거의 그대로, 훑기는 비례해서 늘어나는 것**을 표 · 그래프로 (O(log n) vs O(n) 을 눈으로).
- 운영체제 파일 캐시 영향을 적는다 (같은 파일을 두 번째 훑을 때 더 빠름 — 첫 실행 / 데운 뒤 둘 다).

## 6. Phase 3 — API 서버

### 6-1. API

| 메서드 · 경로 | 요청 | 응답 |
|---|---|---|
| `POST /query` | `{"sql": "SELECT …; INSERT …"}` | `200 {"results": [{"type": "select", "columns": […], "rows": […], "plan": "index-eq", "ms": 0.1}, …]}` |
| `GET /tables` | — | `{"tables": [{"name": "users", "columns": […], "rows": 1000000}]}` |
| `GET /health` | — | `{"ok": true, "pool": {"workers": 8, "busy": 3, "queued": 0}}` |
| 오류 | — | `400` SQL 오류 `{"error": "…", "line": 1, "col": 15}` · `404` 없는 경로 · `405` · `413` 본문 1MB 초과 · `503` 대기열 가득 · `500` 내부 오류 — **모든 응답 JSON** |

### 6-2. 스레드 풀 구조

```
메인 스레드: accept() ─▶ 연결을 대기열에 넣음 ─▶ (가득 차면 바로 503 응답 후 닫기)
                              │
                ThreadPoolExecutor(max_workers=N)   ← 스레드 N 개를 미리 만들어 재사용 (요청마다 새로 만들지 않음)
                 ├─ 작업 스레드 1: 요청 읽기 → Engine.execute → 응답
                 ├─ 작업 스레드 2: …
                 └─ 작업 스레드 N
```
- 표준 `ThreadingHTTPServer` 는 **요청마다 새 스레드**라 과제의 "스레드 풀" 이 아니다 → `HTTPServer.process_request` 를 바꿔 연결을 `executor.submit` 으로 넘긴다.
- **대기열 한도**(예: 작업자 수 × 4)를 둬서 몰릴 때 메모리 · 지연이 끝없이 늘지 않게 `503` (백프레셔).
- 요청 읽기 제한 시간(408) · 본문 1MB(413) · 쿼리 실행 제한 시간 · `GET /health` 의 풀 상태 — Mini Redis 에서 겪은 문제(대기열 5 · 느린 클라이언트 · 413 RST)를 처음부터 반영.
- 종료: Ctrl+C → 새 연결 받기 중단 → 진행 중 작업 끝날 때까지 기다림(`shutdown(wait=True)`) → 파일 닫기.

### 6-3. 동시성 — 무엇이 깨질 수 있나

| 위험 | 장면 | 막는 방법 |
|---|---|---|
| id 중복 | 두 INSERT 가 동시에 "다음 id = 101" 을 읽음 | id 부여 · 파일 붙이기 · 인덱스 등록을 **한 쓰기 락 안에서** |
| 파일 줄 섞임 | 두 스레드가 동시에 같은 파일 끝에 씀 | 같은 쓰기 락 |
| B+ 트리 분할 중 읽기 | 분할 도중 노드를 읽으면 키를 놓침 | 읽기는 읽기 락 |
| 읽는 중 offset 이 아직 안 써짐 | 인덱스엔 있는데 파일엔 아직 없음 | 파일에 쓰고 `flush` 한 **뒤에** 인덱스 등록 |
| 같은 파일 핸들 `seek` 경쟁 | 스레드 A 가 seek 한 뒤 B 가 seek | 읽기는 `os.pread(fd, n, offset)` (위치를 공유하지 않음) 또는 스레드별 핸들 |

- **테이블마다 읽기-쓰기 락(RWLock)**: 읽기(SELECT)는 여럿이 동시에, 쓰기(INSERT)는 혼자. 표준 라이브러리에 없으므로 `threading.Condition` 으로 직접 구현하고, 쓰기가 굶지 않게(쓰기 대기 중이면 새 읽기를 기다리게) 한다. 단위 테스트로 "읽기 둘이 동시에 들어감 · 쓰기는 혼자" 를 확인.
- 문장 여러 개를 한 요청에 보내면 문장마다 락을 잡는다 (트랜잭션은 하지 않음 — 보고서에 한계로 적기).
- **GIL**: 파이썬은 한 번에 한 스레드만 파이썬 코드를 실행한다. 그래도 파일 읽기 · 소켓 대기 중에는 GIL 을 놓으므로 I/O 가 섞인 요청은 겹쳐 돈다. "스레드 풀로 몇 배 빨라지나" 를 정직하게 측정해 적는다 (작업자 1 / 4 / 8 / 16, 읽기만 · 쓰기만 · 섞어서). CPU 위주 쿼리는 거의 안 빨라질 것으로 예상 — 이유까지 설명.

### 6-4. 테스트 (Phase 3)

- 실제 서버를 빈 포트에 띄우고 `http.client` 로 요청 (Mini Redis 와 같은 방식).
- 동시성: 스레드 20개가 각자 INSERT 500번 → id 10,000개가 **빠짐 · 겹침 없이** 1 ~ 10000, 파일 줄 수 = 인덱스 크기 = 10,000.
- 읽기 · 쓰기 섞기: 쓰는 동안 읽은 결과가 항상 "있는 행은 완전한 행" 인지.
- 대기열 가득 → 503, 느린 클라이언트 → 408, 큰 본문 → 413, 잘못된 JSON · SQL → 400 (줄 · 칸 포함).
- 서버를 껐다 켜도 데이터 · 다음 id 가 이어지는지 (인덱스 다시 만들기).

## 12. 구현하며 정한 것 (계획 검토 13가지 반영)

| # | 계획 검토에서 나온 문제 | 구현 |
|---|---|---|
| 1 | 테이블 이름이 파일 경로가 됨 | 이름은 `[a-z_][a-z0-9_]{0,63}` (토크나이저 · 카탈로그 둘 다). SQL 의 이름은 카탈로그 사전에서 찾기만 하고 경로를 만들지 않음 |
| 2 | 100만 건 SQL 을 통째로 토큰화하면 메모리 폭발 | 토크나이저 · 파서가 제너레이터 — `;` 까지만 모아 문장 하나씩 실행 |
| 3 | API 결과가 너무 큼 | SELECT 응답 최대 1,000행. 엔진은 넘는 행을 담지 않고 세기만 (`truncated` · `total`) |
| 4 | 스레드 풀 + 연결 재사용 → 쉬는 연결이 작업자를 붙잡음 | 응답마다 연결을 닫음 (HTTP/1.0) |
| 5 | 쓰는 중 훑기가 반쯤 쓰인 줄을 봄 | 읽기-쓰기 락 + 훑기는 시작할 때의 파일 크기까지만 |
| 6 | 파일 쓰기 ↔ 인덱스 등록 사이 실패 | 쓰기 전 크기 기억 → 실패하면 그 크기로 자르고 쓰기 핸들 다시 열기. 인덱스 · 다음 id 는 쓰기 성공 뒤에만 바꿈 |
| 7 | 비교 규칙 | 숫자 열 ↔ 숫자, TEXT ↔ 문자열만 (섞으면 실행 전 오류) · NULL 은 항상 거짓 · 문자열은 유니코드 순서 |
