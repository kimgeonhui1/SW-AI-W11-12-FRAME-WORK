# 미니 DBMS

SQL 파일을 읽어 **파싱 → 실행 → 파일에 저장**하는 처리기(Phase 1)에 **B+ 트리 인덱스**를 붙이고(Phase 2), 이것을 엔진으로 두는 **스레드 풀 API 서버**(Phase 3)까지 만든 작은 DBMS 입니다.

- 언어: Python 3.10 이상, **표준 라이브러리만** (설치할 것 없음) · Python 3.14 · macOS (Apple M5) 에서 검증
- 브랜치: `feat/Kimjunwoo-DBMS` (김준우)
- 테스트: **56개** 통과 (`python -m unittest`, 약 8초)
- 성능 (100만 건): `WHERE id = ?` **0.010ms** vs `WHERE name = ?` **731ms** — 약 **75,000배** (5장)
- 계획 문서: [설계.md](./설계.md)

## 1. 빠른 시작

`projects/dbms` 에서:

```bash
python -m mini_dbms examples/phase1.sql                 # Phase 1: SQL 파일 실행
python -m mini_dbms -e "SELECT * FROM users WHERE id = 1"
python -m mini_dbms                                     # 대화형 (; 로 끝내면 실행, exit 로 종료)
python -m bench.bench                                   # Phase 2: 1만 · 10만 · 100만 건 성능 비교 (약 1분)
python -m mini_dbms.server --port 8080 --workers 8      # Phase 3: API 서버
python -m unittest                                      # 테스트 56개
```

API 사용 예:

```bash
curl -s localhost:8080/query -d '{"sql": "INSERT INTO users (name, age) VALUES ('kim', 25); SELECT * FROM users WHERE id = 1"}'
```

`python -m mini_dbms examples/phase1.sql` 출력 (앞부분):

```
INSERT users 1행 (id 1) · 0.05 ms
+----+---------+------+-----------------+
| id | name    | age  | email           |
+----+---------+------+-----------------+
|  1 | 김준우  |   25 | kim@example.com |
|  2 | O'Brien |   31 | ob@example.com  |
```

## 2. 구조

```
               ┌──────────── 입구 (둘 다 Engine.run(sql) 하나만 부른다) ───────────┐
 SQL 파일 / -e │  cli.py  (Phase 1)                server.py  (Phase 3)            │ HTTP JSON
 ─────────────▶│  표 출력 · 종료 코드              스레드 풀 · 요청 검사 · JSON       │◀──────────
               └───────────────────────────┬───────────────────────────────────────┘
                                           ▼
                  engine.py   문장마다: 파싱 → 테이블 락 → 실행 → 결과 dict
                                           │
          ┌────────────────────────────────┼────────────────────────────────┐
          ▼                                ▼                                ▼
   tokenizer.py → parser.py         executor.py                       rwlock.py
   글자 → 토큰 → 문장(nodes.py)     계획 고르기 · 조건 · 타입 검사      읽기 여럿 · 쓰기 혼자
                                           │
                          ┌────────────────┼────────────────┐
                          ▼                ▼                ▼
                     catalog.py        table.py          bptree.py
                     스키마(열 · 타입)  JSON Lines 파일    id → 파일 위치
```

| 파일 | 하는 일 |
|---|---|
| `tokenizer.py` | 정규식 하나로 글자 → 토큰. 토큰마다 줄 · 칸 번호 |
| `parser.py` · `nodes.py` | 재귀 하강 파서. 문장을 **하나씩** 만들어 넘긴다 (100만 행 파일도 문장 하나 분량만 메모리에) |
| `catalog.py` | `data/<테이블>.schema.json` 읽기 · 이름 · 타입 검사 |
| `table.py` | 데이터 파일 쓰기 · 위치로 읽기 · 훑기, 켤 때 인덱스 다시 만들기 |
| `bptree.py` | B+ 트리 (넣기 · 찾기 · 범위 · 한꺼번에 쌓기 · 규칙 검사) |
| `executor.py` | INSERT 값 검사, SELECT 계획 고르기 · 조건 · 정렬 · LIMIT |
| `engine.py` | 문장을 순서대로 실행, 테이블마다 읽기-쓰기 락 |
| `rwlock.py` | 읽기-쓰기 락 (쓰기 우선) |
| `cli.py` · `server.py` | 입구 |
| `bench/` | 대량 INSERT SQL 생성 · 성능 측정 |

## 3. Phase 1 — SQL 처리기

### 지원하는 SQL

```sql
INSERT INTO users (name, age) VALUES ('kim', 25), ('O''Brien', NULL);   -- 여러 행 · 작은따옴표는 두 번
INSERT INTO products VALUES ('키보드', 39000.5);                          -- 열 목록 생략 = 스키마 순서 (id 제외)
SELECT * FROM users;
SELECT name, age FROM users WHERE age >= 20 AND name != 'kim' ORDER BY age DESC LIMIT 10;
SELECT * FROM users WHERE id >= 100 AND id < 200;                        -- id 범위 → 인덱스
EXPLAIN SELECT * FROM users WHERE name = 'kim';                          -- 실행하지 않고 계획만
-- 주석, /* 여러 줄 주석 */ · 키워드는 대소문자 무시
```

비교: `=` `!=` `<>` `<` `<=` `>` `>=` · 값: 정수(64비트) · 소수 · `'문자열'` · `NULL`
CREATE · UPDATE · DELETE · JOIN · OR 은 없습니다 (과제 범위: INSERT · SELECT, 테이블은 이미 존재).

### 저장 — 테이블 하나 = 파일 두 개

```
data/users.schema.json   {"columns": [{"name": "id", "type": "INT"}, {"name": "name", "type": "TEXT"}, …]}   ← 미리 있음
data/users.jsonl         [1,"김준우",25,"kim@example.com"]                                                 ← INSERT 가 붙임
                         [2,"O'Brien",31,"ob@example.com"]
```

- **JSON Lines** (한 줄 = 한 행 = JSON 배열). 값 안의 줄바꿈 · 따옴표 · 쉼표를 json 이 이스케이프하므로 **항상 한 줄 = 한 행**이고, 숫자 / 문자열 / NULL 타입이 그대로 남습니다. CSV 는 값 안의 줄바꿈 때문에 "위치에서 한 줄만 읽기"가 깨집니다.
- 첫 열 `id` 는 자동 부여(1, 2, 3 …). 직접 넣으면 오류.
- 타입: `INT` · `FLOAT` · `TEXT`. INT 열에 소수(25.5)는 거부(몰래 자르지 않음), FLOAT 열의 정수는 소수로.

### 규칙 · 엣지 케이스

| 상황 | 동작 |
|---|---|
| SQL 오류 | `오류 (2번째 문장) 3번째 줄 18칸: …` — 위치와 무엇이 와야 했는지. 종료 코드 1 |
| 여러 문장 중 하나가 틀림 | 앞 문장은 실행된 채로 그 문장에서 멈춤 (트랜잭션 없음) |
| 여러 행 INSERT 중 한 행이 틀림 | **한 행도 안 들어감** (모두 검사한 뒤에 쓴다) |
| 없는 테이블 · 열 | 있는 테이블 · 열 목록을 함께 알려 줌 |
| `age = 'x'` (숫자 열을 문자열과) | 실행 전 오류 (조용히 0행을 돌려주지 않음) |
| `NULL` 비교 | 항상 거짓 (`age = NULL` 도) — SQL 과 같음 |
| ORDER BY 없음 | id 오름차순 보장 · ORDER BY 의 NULL 은 항상 맨 뒤 |
| 쓰다가 실패 (디스크 가득) | 파일을 쓰기 전 크기로 잘라 되돌림 — 파일 · 인덱스 · 다음 id 모두 그대로 |
| 켤 때 마지막 줄이 반쯤 쓰여 있음 | 잘라 내고 경고 / 중간 줄이 손상 → 시작 거부 (종료 코드 2) |
| 테이블 이름 `../x` | 이름은 `[a-z_][a-z0-9_]*` 만 — 데이터 폴더 밖 파일을 건드릴 수 없음 |
| 아주 큰 수 · 닫히지 않은 문자열 · 주석만 있는 파일 | 위치가 있는 오류 / 실행할 문장 0개 |

## 4. Phase 2 — B+ 트리 인덱스

```
                         [ 40 | 80 ]                     ← 안쪽 노드: 길잡이 키
                 ┌─────────┼──────────┐
           [10|20|30]   [40|50|60]  [80|90]              ← 잎: (id, 파일 위치) 정렬
               └── next ──▶ └── next ──▶                  ← 잎끼리 연결 → 범위 검색
```

- **키 = id, 값 = 데이터 파일 안의 바이트 위치.** 찾으면 그 위치에서 한 줄만 읽습니다 (`os.pread` — 스레드끼리 파일 위치를 공유하지 않음).
- 노드당 키 최대 64개 → 100만 건에서 높이 4. 노드 안에서는 `bisect`(이진 탐색).
- **메모리 기반**: 엔진이 켜질 때 파일을 한 번 훑어, 이미 정렬된 id 로 **한꺼번에 쌓기(bulk load)** — 100만 건 0.71초.
- **오른쪽 치우침 분할**: id 는 항상 커지며 들어오므로, 맨 오른쪽 잎이 넘치면 반반이 아니라 "꽉 찬 왼쪽 + 새 키 하나" 로 나눕니다 → 잎 수 절반, 잎 채움 50% → 100% (5장 표).
- 넣을 때마다 규칙(정렬 · 같은 깊이 · 반 이상 참 · 잎 연결 · 키 수)을 확인하는 `check()` 로 order 3 · 4 의 깊은 트리를 무작위 · 순서대로 · 역순으로 시험하고, 결과를 `dict` · `sorted` 와 대조합니다.

### 실행기가 인덱스를 쓰는 때

| WHERE | 계획 | 비용 |
|---|---|---|
| `id = 5` | `index-eq` — 한 점 찾기 → 한 줄 읽기 | O(log n) |
| `id >= 10 AND id < 20` | `index-range` — 잎 연결을 따라감 | O(log n + k) |
| `id = 5 AND age > 20` | `index-eq` 로 줄인 뒤 나머지 조건 검사 | O(log n) |
| `name = 'kim'` · 없음 · `id != 5` | `full-scan` — 처음부터 끝까지 | O(n) |

인덱스로 고른 행에도 모든 조건을 다시 검사하므로, 계획이 어떻든 결과는 같습니다 (테스트로 확인).

## 5. 성능 측정 (`python -m bench.bench --server`)

데이터는 `bench/gen_sql.py` 가 고정 씨앗으로 만든 INSERT 문(1,000행씩)을 **Phase 1 처리기 그대로**(`Engine.run`) 넣었습니다. n 번째 행의 name 은 `user_n` 이라, `id = n` 과 `name = 'user_n'` 이 **같은 한 행**을 찾는 공정한 비교입니다. 시간은 SQL 파싱까지 포함한 사용자 기준, 여러 번 잰 중앙값 (id 1,000번 · name 5번), 파일 캐시가 데워진 상태입니다.

| 행 수 | INSERT 전체 | 파일 | 다시 열기 | 높이 | `id = 1` | `id = 가운데` | `id = 끝` | 없는 id | `name = 가운데` (선형) | 배 | id 범위 1,000행 |
|---|---|---|---|---|---|---|---|---|---|---|---|
| 10,000 | 0.1초 | 0.5MB | 0.01초 | 3 | 0.010ms | 0.010ms | 0.010ms | 0.008ms | 7.4ms | 769 | 1.4ms |
| 100,000 | 0.6초 | 5MB | 0.07초 | 3 | 0.010ms | 0.010ms | 0.010ms | 0.008ms | 72.7ms | 7,520 | 1.4ms |
| 1,000,000 | **6.7초** | 51MB | 0.71초 | 4 | 0.010ms | **0.010ms** | 0.010ms | 0.008ms | **731ms** | **74,996** | 1.4ms |

- 인덱스는 데이터가 100배가 돼도 **0.010ms 그대로**(높이 3 → 4 뿐), 선형 탐색은 **데이터에 비례**(7 → 73 → 731ms). O(log n) 과 O(n) 이 숫자로 보입니다.
- id 범위 1,000행은 크기와 상관없이 1.4ms (찾는 시간 + 1,000줄 읽기).

B+ 트리에 100만 개를 순서대로 넣기 (order 64):

| 분할 | 시간 | 높이 | 잎 수 | 안쪽 노드 | 잎 채움 |
|---|---|---|---|---|---|
| 오른쪽 치우침 (기본) | 0.25초 | 4 | 15,625 | 488 | **100%** |
| 반반 (보통) | 0.27초 | 4 | 31,249 | 975 | 50% |

Phase 3 — 작업자 수별 처리량 (10만 건, 클라이언트 16개, 3초씩, 요청마다 새 연결):

| 작업자 | `id = ?` (요청/초) | 선형 탐색 (요청/초) |
|---|---|---|
| 1 | 5,408 | 19 |
| 4 | 4,945 | 18 |
| 8 | 4,821 | 17 |
| 16 | 4,820 | 17 |

- **작업자를 늘려도 빨라지지 않습니다.** 파이썬은 GIL 때문에 한 번에 한 스레드만 파이썬 코드를 실행하고, 이 쿼리들은 파싱 · JSON · 비교 같은 CPU 일이 대부분이라 겹쳐 돌 틈이 없습니다 (스레드가 많을수록 전환 비용으로 조금 느려짐).
- 그래도 스레드 풀이 하는 일은 있습니다: 느린 선형 탐색이 도는 동안 다른 연결을 받아 두고, 소켓 · 파일을 기다리는 동안 다른 요청을 진행하며, 한도를 넘으면 503 으로 버팁니다. 진짜 병렬(코어 여러 개)이 필요하면 프로세스를 여러 개 띄우는 방식이 필요합니다 (한계 참고).

## 6. Phase 3 — API 서버

| 메서드 · 경로 | 요청 | 응답 |
|---|---|---|
| `POST /query` | `{"sql": "…; …"}` | `200 {"results": [{"type": "select", "columns", "rows", "count", "total", "truncated", "plan", "scanned", "ms"}, …]}` |
| | SQL 오류 | `400 {"error", "line", "col", "statement", "results": 오류 전 문장들의 결과}` |
| `GET /tables` | | `{"tables": [{"name", "columns", "rows"}]}` |
| `GET /health` | | `{"ok": true, "workers", "busy", "queued"}` |
| 그 밖 | | 404 · 405 · 408(본문을 제때 안 보냄) · 413(1MB 초과) · 503(대기열 가득) · 500 — 모두 JSON |

```
메인 스레드: accept() ─▶ (작업 중 + 기다림) ≥ 작업자 + 대기 한도? ─예─▶ 503 보내고 닫기
                                         └아니오─▶ ThreadPoolExecutor.submit(연결)
작업 스레드 1..N (미리 만들어 재사용): 요청 읽기 → Engine.run(sql) → JSON 응답 → 연결 닫기
```

| 결정 | 이유 |
|---|---|
| `HTTPServer.process_request` 를 바꿔 풀에 넘김 | 표준 `ThreadingHTTPServer` 는 요청마다 새 스레드 — "스레드 풀" 이 아님 |
| 대기 한도(기본 작업자 × 4) → 503 | 몰릴 때 기다리는 연결이 끝없이 쌓이지 않게 (백프레셔) |
| 응답마다 연결 닫기 (HTTP/1.0) | 연결을 재사용하면 쉬는 클라이언트 하나가 작업자 하나를 붙잡는다 → 쉬는 클라이언트 N 명이 풀 전체를 막음 |
| SELECT 응답은 최대 1,000행 (`truncated` · `total`) | `SELECT * FROM users`(100만 행)가 수백 MB 응답이 되지 않게. 엔진은 넘는 행을 담지 않고 세기만 한다 |
| 요청 제한 10초(408) · 본문 1MB(413, 버리고 응답) · 대기열 128 | 느린 클라이언트 · 큰 본문 · 동시 접속 (Mini Redis 에서 겪은 문제를 처음부터 반영) |
| 기본 주소 `127.0.0.1` | 아무 SQL 이나 받는 서버라 인증 없이 외부에 열지 않는다 |

### 동시성 — 테이블마다 읽기-쓰기 락

| 위험 | 막는 방법 |
|---|---|
| 두 INSERT 가 같은 id | id 정하기 · 파일 쓰기 · 인덱스 등록을 **한 쓰기 락 안에서** |
| 파일 줄이 섞임 | 같은 쓰기 락 |
| B+ 트리 분할 도중 읽기 | SELECT 는 읽기 락 (쓰기와 겹치지 않음, 읽기끼리는 동시에) |
| 인덱스는 있는데 파일엔 아직 없는 줄 | 파일에 쓰고 flush 한 **뒤에** 인덱스 등록 |
| 같은 파일 위치(seek)를 두 스레드가 씀 | 위치로 읽기는 `os.pread`, 훑기는 매번 자기 파일 핸들 |
| 쓰기가 영원히 못 들어감 | 쓰기 우선 — 쓰기가 기다리면 새 읽기는 대기 |

테스트: 스레드 8개 × INSERT 50번(엔진), 클라이언트 20개 × 25번(서버) → id 가 **빠짐 · 겹침 없이** 1 ~ n, 파일 줄 수 = 인덱스 크기. 쓰는 동안 읽은 행은 항상 완전한 행.

## 8. 한계

| 한계 | 설명 |
|---|---|
| SQL | INSERT · SELECT 만. UPDATE · DELETE · JOIN · OR · 집계(COUNT) 없음 |
| 인덱스 | `id` 하나만. 다른 열은 항상 선형 탐색 |
| 트랜잭션 | 없음. 여러 문장 중 하나가 틀려도 앞 문장은 되돌리지 않음 (한 INSERT 문장 안의 여러 행은 모두 / 없음) |
| 병렬 | GIL 때문에 스레드를 늘려도 CPU 일은 빨라지지 않음 (5장) |
| 시작 시간 | 인덱스를 파일에 저장하지 않아 켤 때마다 다시 만듦 (100만 건 0.7초) |
| 내구성 | 쓰기는 flush 까지 (운영체제 버퍼). 전원이 갑자기 꺼지면 마지막 쓰기를 잃을 수 있음 — `Engine(sync=True)` 면 매번 fsync |
| 데이터 파일 검사 | 켤 때 열 수 · id 순서만 확인하고 값 타입은 다시 보지 않음 (사람이 파일을 직접 고치면 못 잡음) |
| 보안 | 인증 없음 — 기본 `127.0.0.1` |
